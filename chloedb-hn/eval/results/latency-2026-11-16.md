# Search latency, 2026-11-16

Measured on 2026-11-16 at 07:55 UTC by `eval/latency.py`, 40 queries
([queries-2026-11-16.txt](queries-2026-11-16.txt)), each asked twice of both
engines, one request at a time:

```bash
python3 eval/latency.py --app https://hn.chloetech.ai --queries eval/results/queries-2026-11-16.txt \
  --name latency-2026-11-16 --where "cloud container -> hn.chloetech.ai (DO nyc3), hn4 on node disks"
```

- **Client:** a Linux cloud machine (4 cores), outside DigitalOcean.
- **ChloeDB:** the app at https://hn.chloetech.ai, on a DigitalOcean Kubernetes
  cluster in nyc3: chloedb-hn on one machine, and chloedb-server as a
  coordinator over four shards of one copy each, each shard on its own
  s-8vcpu-16gb-amd machine, its data (about 14 GB) on the machine's own disk
  and read into memory first. 4.78 million stories and 41.1 million comments.
- **Algolia:** hn.algolia.com's public search API, stories, 20 a page.

ChloeDB's number is the app's whole search of stories (the words, the
candidates by text and by meaning, ranking, the count and highlights), as
the app reports it; Algolia's is the `processingTimeMS` it reports. End to
end is the time the client waited, network included.

| ms | ChloeDB, first ask | ChloeDB, again | Algolia, first ask | Algolia, again |
|---|---|---|---|---|
| server, median | 99.5 | 67.2 | 17.0 | 17.0 |
| server, p90 | 268.8 | 82.7 | 34.3 | 34.3 |
| server, p99 | 389.3 | 96.5 | 72.5 | 72.5 |

The network alone was 30.6 ms at the median to the app and at least 189.5 ms
to Algolia from this client, so the end-to-end comparison depends on where

## The simplest searches, against Algolia

At 08:24 UTC the same day, `eval/plain.py` asked the same 40 queries as the
simplest statements ChloeDB runs, sent to the coordinator itself, with the
time the server reports. BM25 here reads titles only, while Algolia also
searches links, authors and text. Each statement carried a parameter of its
own, so the answer cache never answered. The numbers are first asks: asked
again, every statement took 2 to 6 ms, because the filter cache already held
the match, while Algolia stayed at 16.5 ms.

| ms, first ask | median | p90 | p99 |
|---|---|---|---|
| Algolia, `processingTimeMS` | 16.5 | 32.0 | 35.2 |
| BM25 of the titles, every word, top 20 | 15.3 | 24.5 | 36.4 |
| its `COUNT(*)` | 3.0 | 4.0 | 19.4 |
| `title ILIKE '%query%'` (FM-index), first 20, no order | 8.2 | 70.3 | 782.3 |
| its `COUNT(*)` | 5.1 | 74.9 | 2629.7 |
| the app's Fast mode, its whole request | 23.1 | 43.9 | 82.2 |
| the app's Fast mode, end to end | 61.7 | 84.0 | 402.3 |
| Algolia, end to end | 249.7 | 292.1 | 354.0 |

The substring index is slow on short, common text. "rust" is also in
"trust", so it matched 36,001 titles. When a pattern occurs that often, the
index reads the stored titles instead: the count of "rust" took 4.0 s, and
the first 20 titles for "bitcoin" took 1.1 s. It matches the query as one
string, so 6 of the 40 queries ("postgres vs mysql") found nothing. Every
query's numbers are in [plain-2026-11-16.json](plain-2026-11-16.json).
