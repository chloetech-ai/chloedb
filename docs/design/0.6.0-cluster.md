## Summary

A ChloeDB cluster today is a set of shards, each a primary and its replicas
that agree through a Raft-shaped protocol, and coordinators that route
queries over them. The shards' protocol is careful and is checked by a
deterministic simulator and a chaos run. Everything above it is not: the
cluster map, the tables' schemas, rank profiles, functions, API keys and
running jobs are each spread by "tell every server and serve what they agree
on", with no single place that decides. That is why the map can fork when two
coordinators change it (E-2), why a failed `ALTER TABLE` takes a table
offline (E-5), why removed copies can depose a live primary (E-1), and why
scrolls, moves and plans break when a second coordinator is added (E-3, A6).

This proposal gives the cluster's metadata one home and keeps the rest:

1. **A metastore.** A small replicated log, three or five voters, built on
   [raft-rs](https://github.com/tikv/raft-rs) (TiKV's Raft library, a pure
   state machine with no I/O of its own, which fits the way `cores/` is
   written and the simulator runs it). It holds the slot map, each shard's
   members and identity, the catalogue of tables, profiles and functions,
   API keys, containment rules and the state of every running job.
2. **A controller.** One coordinator at a time, chosen by a lease in the
   metastore and fenced by its epoch, runs every change: slot moves, plans,
   DDL, joins and removals of copies. Other coordinators serve queries and
   forward admin calls to it. The operator talks to the controller, not to
   whichever pod a Service picks.
3. **Shards that know who they are.** Every replication call carries the
   cluster id, the shard id, the shard's generation and its membership
   version, so a copy of another shard, or one removed while it was down, is
   refused rather than followed. Elections stay inside the shard: they never
   wait on the metastore.
4. **Named read levels.** `primary`, `session` (the default), `bounded` and
   `any`, with a replica refusing every read but `any` once its primary has
   been silent for longer than the lease (E-4).
5. **An archive and point-in-time recovery.** Each shard's primary uploads
   its committed transactions to object storage, beside periodic
   checkpoints, and the controller takes cluster-wide restore points by
   holding writes on a mark for one round trip. Restoring builds a new
   cluster from any restore point, or each shard as of a time.
6. **Proof outside the simulator.** The real `replication.rs`, coordinator
   and shard service under simulated time, network and disk; recorded client
   histories checked for linearizability and session guarantees; and a
   Jepsen-style harness on real processes with partitions, clock jumps, lost
   writes to disk and membership changes during faults.

Cross-shard transactions stay out of 0.6.0. A write spanning shards commits
per shard, as now, and the documentation says so plainly (see
[Not in this release](#not-in-this-release)).

## Where things stand

What #405 (0.2.0) and the cluster-safety branch already fixed, and what is
left for this design. Finding ids are the audit's.

| area | today | after 0.2.0 and the safety branch | left for 0.6.0 |
|---|---|---|---|
| A new primary counting old-term writes (Raft's figure 8, E-0a) | lost acknowledged writes | fixed: a no-op at the start of each term | nothing |
| Membership changes (E-0c) | any number at once, no majority check | one copy at a time, with a majority check, or `accept_data_loss` | the member *list* is not carried, only a version and a count |
| Removed copies coming back (E-1) | can depose the live primary | a copy refuses `Replicate`, `Restore` and `Verify` from a primary with an older membership version | two removed copies still agree with each other and can elect one of themselves |
| The cluster map forking (E-2) | 5 of 2,000 simulator seeds with two coordinators | operator-run coordinators hold a Kubernetes Lease and keep the map in doubt in it | no fix off Kubernetes; the Lease is not a fence |
| Scroll cursors (E-3) | only on the coordinator that made them | unchanged | forward by the cursor's owner |
| Replica staleness (E-4) | unbounded | unchanged (client sessions help those who use them) | read levels, and a bound for all but `any` |
| DDL across shards (E-5) | a failure on one shard drops the table | unchanged | two steps through the catalogue |
| Shard identity (E-11) | none: any primary with the token is followed | unchanged | cluster and shard ids in every call |
| Refusals by message text (E-12) | coordinators parse error sentences | write outcomes moved to a header | typed refusals for every one a peer acts on |
| State held by one coordinator (A6) | scrolls, moves, plans, map in doubt, cloud records | cloud create refused without durable state | jobs and records in the metastore |
| Protocol versions (A7) | 1 to 20 spoken at once | unchanged | floor at 20 |
| Backups | per-copy checkpoints | unchanged | archive, restore points, PITR |

## Goals

- **One decider for metadata.** Every change to the map, membership,
  catalogue, keys and jobs is a command committed in one linearizable log
  before any server acts on it. Two coordinators cannot both give epoch N.
- **Coordinators that are interchangeable.** Any coordinator answers any
  query and any admin call; a coordinator restart loses no job and no map.
- **A removed or misdirected copy can do no harm.** It is refused by identity,
  not by luck of timing.
- **Reads whose freshness is stated.** Each read level has a definition a
  client can rely on and a test that checks it.
- **Recovery to a point in time**, for the whole cluster at a restore point,
  and for each shard at any moment within the archive's window.
- **Evidence a reviewer outside the project can rerun.**
- **No new dependency on Kubernetes for correctness.** The same design runs
  from `chloedb-server --local DIR` on a laptop to the operator.

## Non-goals

- Atomic writes across shards (two-phase commit). See
  [Not in this release](#not-in-this-release).
- Replacing the shards' replication with a Raft library. The audit's option
  (b) for A1 stays open; this release earns the evidence to decide it.
- Per-table shard counts, automatic split and merge, zone-aware placement
  beyond what the operator does today.
- Moving rows by shipping segments instead of rows (A5). It needs the
  metastore's jobs, so it comes after.
- Following between clusters (`follow.rs`). Its third ordering protocol is
  left as is.

## The design at a glance

```text
                 clients
                    │  HTTP / gRPC
         ┌──────────┴──────────┐
         │ coordinators (any)  │  route queries, forward admin calls
         │  one is controller ◄┼──── lease + epoch in the metastore
         └──┬───────────────┬──┘
   watch    │               │  Slots, Configure, DDL (from the controller)
 ┌──────────▼───┐     ┌─────▼──────────────────────────┐
 │  metastore   │     │ shards: primary + replicas     │
 │  3 or 5      │◄────┤ (cluster id, shard id,         │
 │  voters      │watch│  generation, membership)       │
 └──────┬───────┘     └─────┬──────────────────────────┘
        │ snapshots         │ committed transactions, checkpoints
        └────────┬──────────┘
          ┌──────▼──────┐
          │   archive   │  object storage: s3://…/<cluster id>/
          └─────────────┘
```

Three roles, which can share processes on small clusters:

| role | holds | how many | volume |
|---|---|---|---|
| metastore voter | the metadata log and its snapshots | 3 (or 5, or 1 on one machine) | small (hundreds of MB) |
| coordinator | nothing durable; one of them is the controller | any | none |
| shard server | a database, `<db>.replication`, `<db>.slots` | shards × copies | the data |

## The metastore

### What it holds

| section | contents | today |
|---|---|---|
| `cluster` | cluster id (UUID, made once), name, the protocol floor, the archive's location | none |
| `shards` | per shard: shard id (UUID), index, generation, members (copy id, URL, state `joining`, `member`, `leaving`, `removed`), the membership version the controller last committed | each primary's `<db>.replication`, the coordinator's `--shards` |
| `map` | the slot map: epoch, owner of each of the 4,096 slots, the move under way | each shard's `<db>.slots`, the coordinator's memory |
| `catalogue` | tables (name, table id, schema version, schema, state `active`, `altering`, `dropping`), rank profiles, versioned functions, containment rules | each shard's manifest; served if all agree |
| `keys` | API keys (hashes only), scopes, revocations | merged between servers by `keysync.rs` |
| `jobs` | moves, plans, DDL rollouts, copy joins, restore points: kind, steps, state, owner epoch | one coordinator's memory |
| `controller` | holder, epoch, lease expiry | none (a Kubernetes Lease on the safety branch) |
| `points` | restore points: name, time, each shard's `(generation, term, seq)` | none |
| `cloud` | records of clusters made through the Cloud view, their expiry | `--cloud-file` or memory |

The state is small: a cluster of 64 shards with 3 copies, 200 tables and
10,000 keys is a few megabytes. Rows and audit lines do not go here: the
metastore changes when the cluster's shape changes, not when data does.

### The algorithm: raft-rs

The metastore is a Raft group built on raft-rs. raft-rs is a state machine:
the caller feeds it messages and ticks and carries out what its `Ready`
says (persist these entries, send these messages, apply these committed
entries). That is how `cores/shard.rs` and `cores/slots.rs` are already
written, so the same driver runs it in the server and in `chloedb-sim`, on the
simulator's clock and network, with the simulator's injected faults.

It brings what the home-grown shard protocol lacks and the metastore needs:
log truncation of a diverged suffix, membership changes in the log (single
server and joint consensus), learners (non-voting members that catch up
before they vote), pre-vote and check-quorum, and leases for reads
(`ReadIndex` and lease-based reads). It is the Raft that TiKV runs in
production, with years of testing behind it. See
[Alternatives](#alternatives-considered) for why not openraft, etcd, the
Kubernetes API or the shards' own protocol.

### Where the voters run

| mode | when | voters |
|---|---|---|
| in-process, one voter | `chloedb-server --local DIR`, one machine, tests | 1, inside the coordinator, its log in `DIR/meta/` |
| beside shards | bare metal and small clusters | 3 shard servers also run a voter (`--meta-voter`), each with its own `meta/` directory beside its database |
| dedicated | the operator's default | a `<cluster>-meta` StatefulSet of 3 small pods (`chloedb-server meta`), 1 GiB volumes |

Dedicated voters are the default on Kubernetes because they keep the
metastore's availability apart from shard pods that the operator restarts,
moves and deletes as it scales. On five or more nodes across zones,
`spec.meta.voters: 5` survives the loss of two.

### Commands

Every change is a command proposed to the leader and applied in log order.
A command names the versions of the sections it read and the controller
epoch it holds, and is refused if either moved, so a controller that acted on
a stale view or lost its lease changes nothing:

```text
Command {
  controller_epoch: u64,          // 0 for commands any coordinator may send (keys, contain rules)
  if_versions: [(section, u64)],  // optimistic check: refused if any section changed since read
  op: SetMap | SetMembers | BumpGeneration | AlterTable | PutKey | RevokeKey
      | StartJob | StepJob | EndJob | TakeLease | RenewLease | PutPoint | …,
  who: string,                    // the key or service account behind it, for the audit trail
}
```

Each applied command raises its section's version and the metastore's
index. The log is the audit trail of every administrative change: who, what,
when, and what it replaced.

### Reads and watches

- **Linearizable reads** go through the leader with `ReadIndex`: the
  controller reads this way before it acts.
- **Watches** stream committed changes from an index on (`Watch(from)`).
  Coordinators watch everything; shard servers watch their own shard's
  record, the map and the catalogue. A watcher that falls behind the
  snapshot is sent the snapshot and resumes from its index.
- **Cached state.** Every coordinator and shard keeps the last state it
  applied and serves from it while the metastore is unreachable. Queries,
  writes and shard failover never wait on the metastore; only changes do.

### On disk: `meta/`

```text
meta/HARDSTATE                 term, vote, commit index, crc32c
                               (write to a temporary name, fsync, rename, fsync the directory)
meta/log-<first index:020>     entries in order: len u32 | crc32c u32 | term u64 | index u64 | kind u8 | payload
meta/snap-<index:020>-<term:020>   the state machine at that index: protobuf, then crc32c
meta/ID                        the voter's id and the cluster id, written once
```

Log files roll at 64 MiB and are deleted once a snapshot covers them (two
snapshots are kept). The payload is a protobuf `Command`, so fields can be
added; a voter that reads a command kind it does not know stops applying
and refuses to vote, rather than skip it. The format is new and owned by
this design; it shares nothing with the database's files.

A ChloeDB database was considered as the storage for the log (dogfooding,
SQL over the metadata) and turned down for the first version: a bug in the
engine should not be able to corrupt the thing that decides who owns the
data. The state is exposed read-only as SQL through the coordinator
(`system.shards`, `system.map`, `system.jobs`, …) instead.

### On the wire

A new gRPC service beside `Strata`, in the same package:

```text
service Meta {
  rpc Raft(stream RaftMessage) returns (stream RaftMessage);   // between voters
  rpc Propose(Command) returns (Applied);                      // to the leader; others forward
  rpc Read(MetaReadRequest) returns (MetaState);               // linearizable or cached
  rpc Watch(WatchRequest) returns (stream MetaChange);         // committed changes from an index
  rpc Status(Empty) returns (MetaStatus);                      // leader, voters, indexes, lag
}
```

Voters call each other with the cluster token, as servers do today. Mutual
TLS between servers is a separate change, but the design does not get in its
way.

## The controller

One coordinator is the controller. It takes the lease with a `TakeLease`
command (holder, a new epoch one above the last, expiry), renews it every
second for 10 seconds at a time, and every command it sends carries its
epoch. A coordinator that loses the lease (expiry, partition, restart) can
still send commands, and the metastore refuses them: the epoch is the fence,
not the clock. Expiry decides only when another coordinator may take over.

The controller runs every job: slot moves, plans, DDL rollouts, adding and
removing copies, restore points, the rebalance after a shard is added. Each
job's state lives in `jobs`, and each step is committed before it is acted
on, so a new controller resumes a job from its last committed step. Every
step the shards carry out is idempotent by an epoch or a version (a map
epoch, a schema version, a membership version), so a step done twice is
harmless.

Other coordinators forward admin calls to the controller (`peers::post`,
which exists) and answer from their watched state. The command center's
pages read the same state wherever they are served.

**The operator** calls the cluster's Service as today, and any coordinator
forwards to the controller. The interim Kubernetes Lease on the safety branch
(`operator/lease.rs`) is retired once the metastore is on. The operator's
own reconcile loop keeps choosing *what* the cluster should be; the
controller decides the order of the steps and refuses one that conflicts
with a running job.

## Shards under the metastore

### Identity

`<db>.replication` gains three fields, written once when the copy joins its
shard:

```json
{"id": "a0-7f3c", "cluster": "2b1f…", "shard": "9e04…", "generation": 3,
 "role": "replica", "member": true,
 "config": {"version": 12, "members": ["a0-7f3c", "a1-c210", "a2-0d9e"]}}
```

`Vote`, `Replicate`, `Restore`, `Verify` and `Configure` carry
`(cluster, shard, generation, config version)`. A receiver refuses a call
whose cluster or shard is not its own (E-11), whose generation is older than
its own, or whose sender is not in the membership it knows. Older binaries
read the file and ignore the new fields, so a downgrade within the window
below keeps working.

### Membership as a list

Today the membership a primary ships is a version and a count of copies
(`Kept::config`); a candidate counts its majority from its own copy of the
map. 0.6.0 ships the list of copy ids with the version, and a copy uses the
newest list it holds to count votes and acknowledgments. Changes stay one
copy at a time (Raft's single-server rule, which is safe now that a new
primary commits a no-op of its term first), and a change commits when a
majority of the *new* list holds it.

The controller drives each change: it commits the desired membership in the
metastore (`SetMembers`, with the shard's version), sends `Configure` to the
primary, and records the version the primary reports. If the primary changes
meanwhile, the job resends to the new one; the shard's version makes the
resend a no-op if it already happened.

Elections stay inside the shard. A shard elects a new primary when its
primary is silent even if the metastore is down, which is the property the
system has today and must keep.

### Forced recovery and generations

When a shard loses a majority of its copies for good, someone may accept
the loss of the writes only those copies held (`accept_data_loss` today).
In 0.6.0 that is a metastore command, `BumpGeneration`, which records the
shard's new generation and its surviving members, and only then is the
survivor configured. Every copy of the old generation is refused by every
copy of the new one.

The scenario of E-1: shard {A, B, C}, B and C stop for good, the shard is
recovered to {A} at generation 4, D and E join. B and C come back with their
volumes at generation 3. They can still elect one of themselves (they are a
majority of the list they know), but every call they make to A, D or E is
refused with `OLDER_GENERATION`. On that refusal a copy reads its shard's
record from the metastore, finds itself not a member, and goes to the state
`removed`: no reads, no writes, no votes, no calls. The controller later
wipes and rejoins it, or the operator deletes it. No write of generation 4
is touched.

### Typed refusals (E-12)

Every refusal a peer acts on carries a typed detail in the gRPC status
(`grpc-status-details-bin`), so routing never depends on message text:

```text
message Refusal {
  enum Reason {
    OTHER = 0; OLDER_MAP = 1; NEWER_MAP = 2; NO_MAP = 3; NOT_PRIMARY = 4;
    FENCED = 5; OLDER_GENERATION = 6; NOT_MEMBER = 7; WRONG_SHARD = 8;
    OVERLOADED = 9; NOT_APPLIED = 10; IN_DOUBT = 11; STALE_READ = 12;
  }
  Reason reason = 1;
  uint64 epoch = 2; uint64 term = 3; uint64 generation = 4;
  string primary_hint = 5;   // the copy to ask instead, when known
}
```

The sentences stay in the status message for people.

### The protocol floor (A7)

0.6.0 sets `MIN_PROTOCOL` to 20, the protocol of 0.2.0, and deletes the
branches for older peers, FNV routing among them. A 0.6.0 coordinator
refuses a shard below 20 with a message naming the version to upgrade to.
The new protocols:

| protocol | adds |
|---|---|
| 21 | cluster, shard, generation and the member list in replication calls; typed refusals |
| 22 | maps and DDL carrying the metastore index and schema version they were committed at |
| 23 | read levels and the primary's lease time on heartbeats |
| 24 | restore-point marks and archive status in `Hello` |

## The slot map without forks

The map's epochs are assigned by the metastore. A move is a job whose every
phase (`copying`, the flip, `cleaning`, or `aborting`) is a new map epoch
committed with `SetMap` before any shard is given it. Since epoch N exists
once, in one place, two coordinators cannot give two maps of the same epoch,
and "the map in doubt" (`Coordinator::doubt`) is no longer needed: a map a
shard did not acknowledge is still in the metastore, and the shard gets it
from its watch or from the controller's next call.

A shard checks maps as `cores::slots::take` does now (older epoch refused,
same epoch must be equal), and from protocol 22 also requires the map's
metastore index to be newer than the index of the map it holds. `<db>.slots`
stays as the shard's cache of its last map, so a shard that restarts while
the metastore is down still serves.

## DDL in two steps (E-5)

A statement such as `ALTER TABLE t ADD COLUMN c` becomes a job:

1. The controller commits `AlterTable{t, from: v, to: v+1, schema}`: the
   table is `altering`.
2. It sends the change to every shard with `validate` (protocol 19), then
   applies it, naming the target schema version rather than the statement.
   A shard already at `v+1` answers that it is, so a resend is harmless.
3. When every shard reports `v+1`, the controller commits the table
   `active` at `v+1`.

While a table is `altering`, coordinators serve the columns both versions
share, so the table never leaves the catalogue. A step that keeps failing
leaves the job waiting with the shard named in `/v1/admin/jobs`; it can be
retried or rolled back (`to: v`), which is a job of the same shape.

Rank profiles and functions follow the same pattern with their own
versions. Creating and dropping tables do too.

## State no coordinator owns (A6, E-3, E-6)

| state | 0.6.0 |
|---|---|
| move jobs, plan runs, DDL rollouts | `jobs` in the metastore, run by the controller |
| scroll cursors | the cursor names the coordinator holding it; another coordinator forwards the next page there. A restart of that coordinator ends its scrolls, as now, and says so. (Cursors carrying every shard's cursor were considered: they are larger and still lose the coordinator's merge buffer.) |
| the record of cloud clusters and their expiry | `cloud` in the metastore. Cloud credentials stay out of it: they come from the pod's identity (IRSA, workload identity) or a Kubernetes Secret named in the spec |
| API keys | `keys` in the metastore; `keysync.rs`'s merge is retired. A revocation is committed once and reaches every server through its watch, within a second at the default watch timing |
| containment rules, alert silences | `catalogue` and `jobs` |
| the audit trail of admin changes | the metastore's log; query and log lines stay in each server's log store |

Moving keys into the metastore touches authentication. It can ship in 0.6.0
or wait for the tenant tokens and OIDC of 0.5.0 to settle; see
[open questions](#open-questions-for-the-owner).

## Read levels (E-4)

| level | what it promises | served by |
|---|---|---|
| `primary` | linearizable: reflects every write acknowledged before the read began | the primary, within its lease (as today) |
| `session` (default) | read-your-writes and monotonic reads within a client session (the clients' `session()`, `min_seq_nos`) | any copy that has applied the session's last seen number, waiting up to `READ_WAIT` |
| `bounded:<ms>` | no older than `ms` (at least the heartbeat interval) | a replica whose primary was heard within `ms`, by the replica's clock |
| `any` | whatever the copy holds | any copy, as today's behaviour |

Whatever the level, a replica refuses reads (with `STALE_READ`) once its
primary has been silent for longer than the primary's read lease, or four
heartbeats when failover is off, unless the read asked for `any`. That
closes the case where a cut-off replica serves old rows indefinitely and
rows appear and vanish as the coordinator rotates between copies.

The coordinator's default becomes `session`: each HTTP connection or client
session carries the highest sequence number per shard it has seen. A request
names another level with `consistency` in its body or the header
`x-chloedb-consistency`.

## Archive and point-in-time recovery

### What is archived

With `--archive s3://bucket/prefix` (or `spec.archive` on Kubernetes):

```text
<prefix>/<cluster id>/
  CLUSTER.json                       cluster id, name, written once
  meta/snap-<index:020>.pb           metastore snapshots, every hour and on every job's end
  meta/log-<first index:020>.pb      metastore entries since the snapshot, uploaded with their commit times
  shards/<shard id>/
    files/<name>                     segment, delete-set and update files of checkpoints, once each by name
    base/<seq:020>.json              a checkpoint: the file names it needs, CURRENT, its last (term, seq)
    log/<first seq:020>.arc          committed transactions from that number on (format below)
  points/<name>.json                 restore points: time, each shard's (generation, term, seq)
```

Checkpoints reuse the directory layout's property that files are named by
content and never change (see [Backups](../chloedb/server.md#backups)): a new
base uploads only the files the previous ones did not have.

### Log objects: `.arc`

The same format holds a shard's archived transactions here and a tenant's
log in [0.7.0](0.7.0-file-per-agent.md#log-objects), so it is designed
once:

```text
header   "STRARC01" | version u32 = 1 | flags u32
         | stream id [16]   (the shard id, or the tenant id in 0.7.0)
         | db_id u64 | generation u64
         | first_seq u64 | last_seq u64 | count u32
         | features_len u32 | features (comma-separated, as the WAL's STRWAL02 header)
entries  count × ( term u64 | seq u64 | commit_ms u64 | len u32 | bytes[len] )
         bytes: one transaction as the primary shipped it (its WAL records, commit last)
footer   crc32c of everything before it u32 | "STRARC01"
```

The entries are exactly what `ReplicateRequest.txns` carries, so a restore
applies them with `Database::apply_shipped`, the path every replica already
runs. `commit_ms` is the primary's clock when the transaction committed,
which the ship log keeps in memory beside each transaction; a transaction
replayed from the WAL after a restart has no such time and takes the time it
was replayed, which is later than its commit by at most the restart. (The
magic is `STRARC01` because `STRLOG01` is already the writer's log record in
`share.rs`.)

### Who uploads, and when

The shard's primary uploads transactions that a majority holds, never ones
that could still be lost by an election, every second or every 8 MiB. Each
object is created with a conditional write (`If-None-Match: *`), so there is
one object per first number. After a failover, the new primary lists the
shard's `log/` and goes on from the last number archived. If an object with
its name already exists, the primary reads it and compares: the same bytes
mean another primary of the shard got there first; different bytes mean two
histories were committed under the same numbers, which is a safety bug, and
the archive stops and raises a critical alert. The archive is a check on the
protocol as well as a backup.

If the archive falls behind the ship log (the store is down, or slow), the
primary uploads a new base checkpoint once the store is back and the gap
between the two is reported as a hole in the recovery window
(`chloedb_archive_gap_seconds`, an event and an alert). With
`archive.required: true`, the primary instead holds its flushes and then
refuses writes (503) until the archive catches up, for users who prefer
unavailability to a hole. The default is best effort with an alert; see
[open questions](#open-questions-for-the-owner).

### Restore points

The controller takes a restore point by asking every shard's primary to hold
clients' writes on a mark (the marks protocol 17 added for switchover),
reading each shard's last `(term, seq)`, committing the point in the
metastore and in `points/`, and releasing the marks. Writes pause for about
one round trip to the slowest primary. Points are taken every 15 minutes by
default and by hand (`POST /v1/admin/points`).

A restore point is the only cluster-wide consistent cut, because writes are
atomic per shard. Restoring to a time instead restores each shard to its
last transaction committed at or before that time, which can split a
multi-shard write; the documentation says so where the option is offered.

### Restoring

```sh
chloedb-server restore --archive s3://bucket/prefix --cluster 2b1f… \
  --to point:nightly-2027-05-01 \      # or time:2027-05-01T14:03:00Z, or seq:<shard>=<n>,…
  --into /restore
```

For each shard it fetches the newest base at or before the target, applies
the `.arc` entries up to the target, and checks the result's digests
(`Verify`'s per-slot sums) against the archive's record where the point has
one. It rebuilds the metastore's state as of the target from the metastore's
archived snapshot and log (so the map, schemas and keys match the data), and
gives the new cluster a **new cluster id**: a restored copy can never be
mistaken for the live cluster by a server of either. The operator takes the
same from `spec.restore: {archive, cluster, to}`.

## Proving it

Three layers, each run in CI or nightly, and a fourth outside the project.

1. **The real code under simulation.** Run `replication.rs`, the shard
   service, the coordinator and the metastore's driver under
   [madsim](https://github.com/madsim-rs/madsim) (simulated tokio, tonic,
   time and network), with ChloeDB's `fault-injection` I/O beneath for torn
   writes, lost fsyncs and full disks. Today the simulator runs the
   decisions in `cores/` over a model database; the bugs #405 fixed were in
   the I/O around them. CI runs 3,000 seeds per world as now; nightly runs
   30,000.
2. **Histories and checkers.** Every simulated and chaos client records each
   operation's invocation and completion (ok, failed, or unknown). Checkers:
   linearizability of single-key registers under `primary` (a
   Wing–Gong–Lowe search, as Porcupine does, in Rust in `chloedb-sim`);
   session guarantees under `session`; the staleness bound under `bounded`;
   per-shard serializability of multi-key batches with list-append workloads
   checked by [Elle](https://github.com/jepsen-io/elle) (run as a separate
   step from its command-line jar). Anomalies across shards are expected and
   are reported, not failed.
3. **`chloedb-jepsen`: real processes.** Five containers or VMs, a metastore of
   three, two shards of three copies, two coordinators, and these faults,
   alone and combined: partitions (majority and minority, a bridge, the
   primary alone, the metastore's leader alone, the controller alone), kill
   and pause (`SIGKILL`, `SIGSTOP`), clock jumps and skew (`libfaketime`,
   `date -s`), slow and failing disks (`dm-delay`, `dm-flakey`), a full disk,
   and changes during faults: copies added and removed, slots moved, tables
   altered, coordinators and voters replaced, restore points taken. A run is
   a fixed workload for 10 minutes with faults every 15 to 30 seconds and a
   final heal, then the checkers above and a ledger of acknowledged writes.
   Nightly on one runner; a longer sweep weekly.
4. **An outside review.** Once layer 3 has run clean for a month, ask an
   independent reviewer (Jepsen, or a university group) to run their own
   tests against 0.6.0 and publish what they find.

## Failure modes

| failure | what happens | what the user sees |
|---|---|---|
| The metastore loses its quorum | Queries, writes and shard failover go on from cached state. No change is accepted: moves pause at their last committed step, DDL waits, keys cannot be made or revoked | admin calls answer 503 `metastore unavailable`; an alert; `/v1/health` names it |
| A voter loses its disk | It is replaced by a learner that catches up and then votes (a membership change in the metastore's own log) | an event; nothing else |
| A majority of voters lose their disks | `chloedb-server meta recover` rebuilds the state from the newest archived snapshot and log, or from what shards and coordinators cached, under a new metastore generation; the old voters are refused | a documented procedure; changes since the last archive upload may be lost and are listed |
| The controller dies in the middle of a move | Its lease expires (10 s); another coordinator takes it with a higher epoch and resumes the job from its last committed step | the move takes longer |
| A controller partitioned from the metastore keeps acting | Its commands carry the old epoch and are refused; it cannot give a map the metastore did not commit | nothing |
| A coordinator routes by an old map | Shards refuse it with `OLDER_MAP`; it reads the map and resends (as now) | a retry inside the coordinator |
| A removed copy comes back with its volume | Refused by generation or membership, goes to `removed` | an event; the operator or controller wipes it |
| A copy is pointed at another shard's primary | Refused with `WRONG_SHARD` | an error naming both shards |
| A replica is cut off from its primary but not from coordinators | It refuses reads after the lease, except `any` | coordinators read other copies |
| A shard's primary cannot reach the archive | It serves as usual; the gap grows and is reported; with `archive.required` it holds writes after a bound | an alert with the size of the hole |
| Two primaries upload different transactions under one number | The second upload finds the first, compares, stops archiving and alerts | a critical alert: a protocol bug, with both objects kept for diagnosis |
| A clock jumps | Leases are measured on each process's monotonic clock; safety depends on epochs, terms and generations, not on time. `commit_ms` and time-based restores use wall clocks and say so | restores by time are as accurate as the primaries' clocks |
| A DDL step fails on one shard | The table stays `altering` and served on its shared columns; the job waits and names the shard | the job in `/v1/admin/jobs` and the Cluster page |
| A restore point's hold cannot reach one primary | The point is abandoned, the marks released, and the controller tries again later | an event |

## Migration from 0.5.x

The order is chosen so that each step can be undone until the last.

1. **Upgrade the binaries** to 0.6.0 with the metastore off. Everything
   behaves as 0.5.x, except that peers below protocol 20 are refused (every
   0.2.0 and later server speaks 20).
2. **Start the voters.** `chloedb-server meta init` (or the operator, when
   `spec.meta` appears) starts the voters and has the controller import the
   cluster as it is: it reads every shard's map and refuses to go on while
   shards disagree or a move is under way (finish or stop it first); it
   reads each primary's membership, the common catalogue (tables that differ
   between shards are listed, and block the import until fixed), profiles,
   functions, keys and containment rules. It makes the cluster id and a shard
   id per shard, and writes them to each copy's `<db>.replication`. Nothing
   yet depends on the metastore.
3. **Switch.** `POST /v1/admin/meta/switch` commits the switch. From then on
   coordinators take the map, catalogue and keys from the metastore, every
   change goes through the controller, and shards refuse a map that carries
   no metastore index. A coordinator still running 0.5.x cannot change the
   map from here on; the operator upgrades all coordinators before step 3.
4. **Archive.** Turning on `--archive` is independent and can follow at any
   time.

**Rolling back.** Before step 3, stop the voters and downgrade. After step
3, `chloedb-server meta export` writes the state back in the old forms
(`--slot-map`, the `--shards` list, keys pushed to every server), and
`POST /v1/admin/meta/switch {"off": true}` lets shards take maps without an
index again; the map's epoch keeps rising, so a 0.5.x coordinator goes on
from it. The fields 0.6.0 added to `<db>.replication` are ignored by 0.5.x.

**On Kubernetes.** The `StrataCluster` resource (`v1alpha1`) gains optional
fields; an old resource keeps working and gets a metastore on the first
reconcile of a 0.6.0 operator:

```yaml
spec:
  meta:
    voters: 3              # 1, 3 or 5; 0 keeps the metastore off
    storage: {size: 1Gi}
  archive:
    url: s3://bucket/chloedb/
    required: false
    pointsEvery: 15m
    keepDays: 14
  restore:                 # make this cluster from an archive instead of empty
    archive: s3://bucket/chloedb/
    cluster: 2b1f…
    to: point:nightly-2027-05-01
status:
  meta: {leader: e2e-meta-1, index: 81234, controller: e2e-coord-5d8f, epoch: 7}
```

## Alternatives considered

**Where the metadata lives.**

| option | for | against | verdict |
|---|---|---|---|
| raft-rs group | a pure state machine like `cores/`, runs in `chloedb-sim`; proven in TiKV; truncation, learners, joint consensus, lease reads | a second consensus implementation beside the shards' protocol; protobuf codec choices; the driver (storage, transport, ticks) is ours to write and test | **proposed** |
| openraft | async API, complete feature set, active | runs its own task loop, so the simulator would run it through madsim rather than step it directly; younger in production than raft-rs | close second; revisit if raft-rs's driver proves costly |
| The shards' own protocol, as a metadata shard | one protocol to harden; the simulator already models it | no truncation, membership outside the log, and the class of bugs #405 fixed; the root of trust would rest on the least proven part | no, until layer 3 has run clean for months |
| The Kubernetes API (Leases, a ConfigMap or the resource's status) | nothing to build on Kubernetes | nothing off Kubernetes, while `--local` clusters and bare metal must be just as safe; not meant as a store for jobs and keys | no; keep the Lease only as the interim fix |
| An external etcd | battle-tested | a new service to run and back up for every user, from laptop to cloud | no |
| CASPaxos registers | a small algorithm, no log | home-grown again; no log for jobs, watches or the audit trail | no |

**Membership in the metastore, rather than in the shard.** Making the
metastore the only source of each shard's members would make every election
wait on it. Keeping the member list in the shard (shipped by the primary,
kept in `<db>.replication`) and the *desired* members in the metastore keeps
failover independent of the metastore and still lets the metastore fence
copies through generations.

**Membership as log entries.** Raft keeps configuration in the log. ChloeDB
flushes its log into segments and truncates it, so a configuration entry
would also need a place in the manifest: a change to the on-disk format. The
member list shipped in `Replicate` and kept in `<db>.replication` gives the
same ordering guarantee for single-copy changes without one.

**A commit time in the WAL.** A new WAL feature (`commit_ms` in every commit
record) would give every transaction an exact time, on disk, on every copy.
It is a format change, and the archive needs the time only for transactions
it uploads, which the primary knows. Proposed: time in the archive only;
the WAL feature stays possible later.

**Replacing the shards' protocol with raft-rs now.** It would remove one
home-grown protocol. It would also replace the part with the most tests and
fixes so far, in the same release that adds the metastore. Proposed: decide
after 0.6.0's evidence, with the metastore as experience with the library.

## Not in this release

- **Atomic writes across shards.** A batch spanning shards commits per shard.
  The validate round (protocol 19) stays a pre-check, and the documentation
  stops implying more: ChloeDB has Elasticsearch's semantics across shards
  and a database's within one. Two-phase commit over the shards' logs, with
  the metastore's jobs as the coordinator's log, is the shape a later design
  would take, for batches that ask for it.
- **Moving slots by shipping segments** (A5), which needs the jobs above.
- **Zone-aware placement and per-table copies.**
- **Mutual TLS between servers.**

## Milestones

Sizes are rough (S: days, M: weeks, L: a month or more), in order:

| | milestone | size | done when |
|---|---|---|---|
| M0 | raft-rs driven by `chloedb-sim`: the metastore's state machine and driver on the model network, with faults | M | 30,000 seeds clean, including leader changes during proposals |
| M1 | `chloedb-server meta`, `meta/` on disk, `Meta` service, watches, `system.*` tables | M | a three-voter metastore survives the chaos tool's kill and partition scenarios |
| M2 | the controller: lease, epochs, jobs; moves and plans moved onto it | M | the simulator's two-coordinator world shows no fork in 40,000 seeds (today 5 in 2,000) |
| M3 | identity, generations, member lists, typed refusals, protocol floor 20 (protocol 21) | M | E-1's scenario as a test passes; refusals routed by type in every caller |
| M4 | DDL in two steps; catalogue, profiles, functions in the metastore (protocol 22) | M | a DDL with a shard down leaves the table served |
| M5 | read levels and the replica's staleness bound (protocol 23) | S | the staleness checker passes in the simulator and the chaos run |
| M6 | archive, restore points, `restore` (protocol 24) | L | a monthly restore drill on the DigitalOcean cluster matches its digests |
| M7 | madsim over the real I/O; histories and checkers | L | runs in CI and nightly |
| M8 | `chloedb-jepsen` | L | a month of nightly runs clean |
| M9 | migration and rollback from 0.5.x, the operator's fields | M | tested on kind and on the DigitalOcean cluster, both ways |

Keys in the metastore (from `keysync.rs`) fit after M4 if the owner wants
them in 0.6.0.

**The gate for 0.6.0**: M0 to M9 done; the simulator, chaos and Jepsen runs
clean for the last four weeks before the tag; no open finding of severity
high or above in the cluster area; one full restore from the archive done on
a real cluster and its result checked.

## Open questions for the owner

1. **raft-rs, as proposed, or openraft?** Either is a long-term dependency
   at the root of the cluster.
2. **Dedicated voters by default on Kubernetes**, or voters beside the first
   three shard servers to save pods?
3. **The new service's name.** The proto package and service are still
   `strata`/`Strata`. Name the new one `Meta` in that package, as proposed,
   or start a `chloedb` package for new services now?
4. **The default read level.** `session`, as proposed, is a behaviour change
   for clients that read from replicas without sessions today. Is that
   acceptable in 0.6.0, or should it be opt-in for one release?
5. **Archive gaps.** Best effort with an alert by default, or
   `required: true` by default?
6. **Keys in the metastore in 0.6.0**, or after the tenant tokens and OIDC of
   0.5.0? It touches authentication.
7. **The protocol floor at 20.** Is any user running a cluster older than
   0.2.0 that must upgrade in place?
8. **Cross-shard writes.** Confirm that 0.6.0 documents per-shard atomicity
   and leaves two-phase commit to a later design.
9. **The outside review.** Is there budget for an independent Jepsen-style
   review after 0.6.0, and who would we ask?
10. **The cloud records' credentials.** Agree that cloud keys leave
    `<db>.aws.json` for pod identity or named Secrets when the records move
    into the metastore.

## One-way doors this design opens

| door | what changes | can it be undone |
|---|---|---|
| shard protocol | protocols 21 to 24; floor at 20; typed refusals | the floor cannot: servers below 20 can no longer join |
| replication | identity, generations and member lists in every call and in `<db>.replication` | the file's new fields are ignored by older servers; calls of older servers are refused once the cluster runs 21 |
| cluster map | maps committed in the metastore first; shards require its index after the switch | yes, by `meta export` and switching off |
| authentication | keys in the metastore (if question 6 says so) | yes, by pushing keys back to every server |
| a new on-disk format | `meta/` | owned by this design; versioned by protobuf fields |
| a new archive format | `STRARC01` objects, the archive's layout | no: archives must stay readable for as long as they are kept; this format is shared with 0.7.0 |
