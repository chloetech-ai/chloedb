## Summary

The demand that is growing fastest in databases is state for agents: one
small, isolated database per customer, user or agent, created in
milliseconds, idle most of the time, deleted with one call. The SQLite
vendors are claiming it ("give every agent its own database"), but their
files cannot rank text, search vectors or walk graphs. ChloeDB's unit is
already one file that does all three. What it lacks is a way to keep
millions of them on object storage and open any of them on demand.

This proposal adds:

1. **An object layout.** A ChloeDB database whose source of truth is a
   prefix on S3 or a store that speaks its API: immutable segment objects
   (the directory layout's files, unchanged) and one small `HEAD` object
   that names them and carries the newest transactions. A commit replaces
   `HEAD` on the condition that nobody else has, so the store itself
   guarantees one writer, with no lease service and no reliance on clocks.
2. **Tenants and tenant servers.** A tenant is one database in the object
   layout. Tenant servers are stateless `chloedb-server` processes that open
   tenants on demand, keep the hot ones in memory and on a local cache, put
   idle ones to sleep, and route each tenant to one node for affinity. A
   small directory lists the tenants; the object store alone is enough to
   rebuild it. A small tenant is literally one `.chloedb` file in the
   bucket, beside its `HEAD`.
3. **Search served straight from object storage**, in three modes: a node
   with a local cache (today's cold tier, generalised), stateless query
   nodes reading byte ranges with a small "hot cache" per database (the way
   Quickwit and turbopuffer work), and a fully static mode in which a WASM
   build of the engine in the browser reads a published `.chloedb` image
   over HTTP range requests, with no server at all.
4. **A blackboard for agent fleets**, the first product on top: a tenant
   template with task claims under expiring leases, exactly-once intake,
   findings deduplicated by meaning, and a timeline, exposed through MCP.

The read-only Postgres wire server and the WASM packaging for other uses,
which the release plan also lists for 0.7.0, are separate documents. The
WASM build here is only what static search needs.

## Can a search engine be served straight from S3?

Yes. Object storage is slow per request (tens to a couple of hundred
milliseconds) but cheap per byte and unlimited in parallel requests, so the
design question is how many *sequential* round trips a query needs and how
many bytes each one moves. ChloeDB's segments are already laid out for it:
every index is a named section at a known offset, the term dictionary is
blocks of 32 terms with a small index over them, postings are blocks with
maximum scores for skipping, IVF clusters are contiguous, and the doc store
is 16 KiB blocks with an index.

| mode | where the query runs | first query on a database | queries after that | writes | good for |
|---|---|---|---|---|---|
| **A. Node with a local cache** | a server holding the database open, fetching what it lacks into RAM and NVMe | 2 round trips to open a small database whole; for a large one, 2 to open and 2 to 3 for the query | as fast as a local file once cached | one writer node | most tenants and indexes |
| **B. Stateless query nodes** | any of N nodes; each reads byte ranges, guided by a hot cache object | 1 round trip for the hot cache, then 2 to 3 per query | 2 to 3 round trips until the node's cache warms | one writer node; readers follow its log | large read-mostly indexes, bursty load, scale to zero |
| **C. Static, in the browser** | a WASM build of the engine in a Web Worker, reading a published image with HTTP `Range` from S3 or a CDN | 1 round trip for the hot cache, then 2 to 3 per query | 0 to 3, as the browser and CDN cache blocks | none (republish) | documentation search, public catalogues, offline-capable apps |

The [round trips per kind of query](#what-a-query-reads), the
[latency model](#latency) and the [cost model](#cost) are below. In short:
a text, vector or hybrid query needs **three sequential round trips** cold
(dictionary, then postings, then the result rows), fewer once the hot cache
holds the dictionary or the database is small enough to fetch whole. HNSW
graphs need one round trip per hop and are the wrong index for this mode;
IVF is the right one.

## Goals

- A database whose only durable copy is in object storage, openable by any
  node, with no local state that matters.
- Creating a tenant in one round trip, opening an idle one in two, deleting
  one in one, with its storage reclaimed after.
- Millions of tenants per bucket, thousands open per node, most of them
  asleep and costing only their storage.
- Every tenant a complete ChloeDB: SQL, hybrid search, graphs, rank
  profiles, the MCP tools, the same file format as a laptop's.
- Search over a large index from stateless nodes, and over a published index
  from a browser, with the number of round trips and their cost known in
  advance.
- The targets of the audit's demo, to be **measured** in milestone M0, not
  assumed: ten thousand tenants on MinIO, cold open plus first hybrid query
  under 100 ms at the median on one small machine, deleting a tenant as one
  call.

## Non-goals

- Queries across tenants. Isolation is the point; a fleet-wide question is a
  query of the directory, or a job that visits tenants one by one.
- More than one writer per tenant at a time. A tenant takes writes on one
  node; others read.
- Write latency below the store's PUT latency. Agents write in bursts and
  tolerate tens of milliseconds; a tenant that cannot is served by a shard of
  a cluster instead.
- A managed cloud service. The audit's advice stands: let "a file per tenant
  on object storage" be the path to a service later, run first by design
  partners in their own accounts.
- Replacing shard replication with shared storage. A cluster whose shards
  keep their data in the object layout is a natural later step, not this one.

## Tenants

A **tenant** is one ChloeDB database in the object layout, under its own
prefix: `s3://bucket/root/<tenant id>/`, where its `HEAD` object is. Its id is chosen by the
application (a customer id, a user id, an agent's name) or made (a UUID).

A **tenant server** is `chloedb-server --tenants s3://bucket/root/`. It holds
no tenant durably. It opens a tenant when a request names one, keeps it open
while it is used, and closes it after it has been idle.

The **directory** is an ordinary ChloeDB table that lists tenants and what
the fleet knows of them (state, size, last use, owner node, quotas,
template). It is an index, not the source of truth: a tenant exists if and
only if its `HEAD` exists, so `chloedb tenants rebuild` lists the root and
writes the directory again.

A **template** is a schema, rank profiles and functions under a name and a
version, published as an empty database image. A new tenant's first base is
that shared image, and its own first base is a full copy (each tenant file
is complete on its own). A newer template version is applied to a tenant
lazily, the next time it opens to write, as an ordinary `ALTER TABLE`.

## The object layout

### Keys

```text
<root>/<tenant>/HEAD                 the one object that is ever replaced, and only
                                     with a condition on the version it replaces
<root>/<tenant>/<incarnation>/
  base/<seq:020>-<epoch:010>.chloedb a packed base: a whole single-file database holding every
                                     transaction up to seq (the single-file format, unchanged)
  base/<seq:020>-<epoch:010>.json    or a spread base: a manifest naming segment objects, up to seq
  seg/<id:010>-<epoch:010>.strata    a segment image (the directory layout's bytes, unchanged)
  seg/<id:010>-<epoch:010>.crc       its ChunkTable, as cold segments have today
  del/…, upd/…                       delete sets and in-place updates, named the same way
  log/<first seq:020>-<epoch:010>.arc   sealed log: committed transactions from first seq on (STRARC01)
  hot/<seq:020>-<epoch:010>.hot      the hot cache for the base of that seq (rebuildable; not a door)
<root>/_templates/<name>/<version>.chloedb   an empty database with a template's schema, shared
```

Everything but `HEAD` is written once, under a name no other writer can
choose, and never changed.

- The **incarnation** is a random id made when the tenant is created. A
  tenant id that is deleted and created again gets a new one, so the old
  tenant's leftovers and the new tenant's objects never share a name.
- The **epoch** is a counter in `HEAD`, raised each time a different node
  starts writing the tenant. A node puts its epoch in the name of every
  object it uploads, so two nodes that both believe they are the writer can
  never overwrite each other's objects. A tenant's database numbers its
  writes, and the epoch is its term.

### HEAD

`HEAD` is the tenant. It is a small object: a JSON header, then the newest
transactions as `STRARC01` bytes, then a crc32.

```json
{"layout": 1, "tenant": "acme-support-bot", "incarnation": "5c0e…", "db_id": 81236417,
 "features": ["seq_no"], "template": {"name": "blackboard", "version": 3},
 "epoch": 7, "writer": "tenant-node-3", "commit": 51822,
 "base": {"key": "5c0e…/base/00000000000000001200-0000000007.chloedb", "seq": 1200},
 "logs": [{"key": "5c0e…/log/00000000000000001201-0000000007.arc", "first": 1201, "last": 1260}],
 "last_seq": 1275,
 "kept": [{"base": "…", "logs": ["…"], "until_ms": 1798761600000}]}
 + the tail: transactions 1261 to 1275
```

A reader needs nothing else to find the database: `HEAD` names the base, the
sealed logs after it, and carries the transactions after those.

### The commit protocol

A write is committed by replacing `HEAD` with a copy that also holds it,
on the condition that `HEAD` is still the version the node last saw
(`If-Match: <etag>` on S3, R2, Azure and MinIO; `ifGenerationMatch` on GCS;
the `object_store` crate's `PutMode::Update`).

1. The node checks each write against its local copy, in order, as a
   database does before it logs one, and gathers those that arrive within
   10 ms (or 1 MiB) into a group. Nothing is visible or acknowledged yet.
2. It puts a new `HEAD`: the old one, with the group appended to the tail
   and `commit` one higher. A node that is not the `writer` named in `HEAD`
   becomes it first, with a put of its own that raises `epoch` and names
   it, and only then uploads anything: a sealed log is named by its epoch,
   and two nodes that both tried for one epoch would otherwise upload
   different bytes under one name. That costs one more put, once, when a
   tenant changes hands. The name a node gives itself is new each time it
   loads the tenant, so a node that reloads takes a new epoch too.
3. If the store accepts, the group is committed: the node makes it visible
   to readers and acknowledges the writes.
4. If the store answers that the condition failed, another node has
   committed since this one last read `HEAD`. Nothing of the group was
   written. The node answers `NOT_WRITER` and reloads the tenant; the client
   library retries, and its idempotency key (the `_sources` row each write
   already leaves) keeps a retry from applying twice.
5. If the put times out and the node cannot tell, it reads `HEAD` again.
   If the group is there (a transaction of its number and the node's epoch
   is the node's own), it is committed. If `HEAD` has moved on without it,
   or the node can replace `HEAD` under a new epoch, the lost put can no
   longer land, since it was conditional on the version before: the write
   failed. Only when the store keeps failing does the node answer that the
   write is in doubt, and then the retry's idempotency key settles it.

In the engine this is one seam. Where a local database appends to its `-wal`
and calls `fdatasync`, a tenant's node replaces `HEAD`. Group commit,
visibility only after durability, and replay are as they are today.

**Why this is safe without a lease or a clock.** There is exactly one
`HEAD`, and every commit is conditional on the commit before it. A node that
was partitioned, paused for a day, or routed wrongly holds an old version:
its next put fails, whatever its clock says and however long it slept. The
store is the only arbiter, so routing can be wrong and nodes can disagree
about who is alive, and the cost is a retry. `commit` makes sure `HEAD`'s
bytes never repeat, since some stores derive an object's version from its
content.

When the tail passes 256 KiB, the node uploads it as a sealed log object and
its next commit moves it from the tail to `logs`. When the log since the last
base passes 4 MiB or 1,000 transactions, and when the tenant goes to sleep,
the node makes a new base: it uploads the packed image (or new segment
objects and a manifest), and its next commit points `base` at it, empties
`logs`, and moves the old base and logs to `kept`. An upload that `HEAD` never
comes to name changes nothing.

### Two kinds of base

- **Packed**: the whole database as one single-file `.chloedb` image, for
  tenants up to a threshold (proposed 32 MiB, to be tuned in M0). Opening it
  is one GET; the node then works on a local copy as on any file. This is the
  common case for agents and the one that makes "a file per agent" literal:
  the object is the same file a laptop opens.
- **Spread**: for larger tenants and for big search indexes, a manifest that
  names segment objects, which are read by range. This is the directory
  layout with every segment cold and `CURRENT` replaced by `HEAD`.

A tenant moves from packed to spread when it grows past the threshold, at
its next base; both read the same way above the storage layer.

### Opening

```text
round trip 1   GET HEAD
round trip 2   GET the base (packed: the image; spread: the manifest and hot cache)
               ∥ GET the sealed logs HEAD lists
then           replay the sealed logs and the tail
```

Two round trips, and no listing. The directory keeps a hint of each tenant's
base, so a node can ask for `HEAD` and the hinted base together: one round
trip when the hint is right, which it is for any tenant that has not made a
new base since. Opening to read costs no write. A node's local copy from an
earlier open is reused if `HEAD` still has the logs that follow it;
`apply_shipped` checks that each batch follows the copy's last transaction.

### Log objects

The [`STRARC01` format of 0.6.0](0.6.0-cluster.md#log-objects-arc): a
header naming the stream (here the tenant's incarnation), the db_id, the
first and last numbers and the features in use, then each transaction as the
engine ships it to a replica (its WAL records, its commit record last) with
its term, number and commit time, and a crc32 of the whole. Replay is
`Database::apply_shipped`, the path every replica already runs. One format
serves a shard's archive, a tenant's sealed logs and the tail in `HEAD`.

### Creating and deleting

- **Creating** a tenant is one put of `HEAD` on the condition that none
  exists (`If-None-Match: *`), with a new incarnation and its base pointing
  at the template's shared image. Creating a tenant that exists fails.
- **Deleting** a tenant deletes `HEAD` first. From that moment the tenant is
  gone for every node: a writer's next commit fails, and a reader finds
  nothing. The objects under its incarnation are then deleted in batches of
  1,000; if that is cut short, the sweep finishes it, since an incarnation
  that no `HEAD` names is garbage.

### Cleanup, retention and time travel

A node deletes only after a commit of its own, and only objects under the
tenant's incarnation that the `HEAD` it just committed does not name, of two
kinds: those that carry an **older epoch** than its own, and those of its
own epoch that it is not still uploading. An object of an older epoch that
`HEAD` does not name can never come to be named: the node that made it can
no longer commit, and a later writer names only what `HEAD` already names
and what it uploads itself. So cleanup needs no grace period and cannot
remove something a commit is about to point at, even if the node doing it
has itself been replaced meanwhile.

- **Retention.** A base and its logs stay in `kept` for
  `--tenant-keep-hours` (proposed 24), so a reader that opened an older base
  can finish, and so a tenant can be opened `AS OF` any transaction in the
  window (the kept snapshots of 0.4.0). A reader that outlives the window
  gets a 404, reads `HEAD` again and reopens. That is a matter of a slower
  query, never of a lost write.
- **Leftover incarnations** and templates no tenant uses are removed by a
  fleet-wide sweep, which lists the root.

### What the store must do

| requirement | why | AWS S3 | GCS | Azure Blob | Cloudflare R2 | MinIO | DigitalOcean Spaces |
|---|---|---|---|---|---|---|---|
| Put only if absent | creating a tenant | yes (since August 2024) | yes | yes | yes | yes | **unknown: to check** |
| Put only if unchanged | every commit | yes (since November 2024) | yes | yes | yes | yes | **unknown: to check** |
| A read sees the last write | a node reads the `HEAD` it must replace | yes (since December 2020) | yes | yes | yes | yes | **unknown: to check** |
| Byte-range GET | spread bases, modes B and C | yes | yes | yes | yes | yes | yes |

The cells are from each vendor's documentation and are not taken on trust:
`chloedb tenants check-store URL` probes a store before use (it creates an
object twice and expects the second to be refused, replaces it with a stale
version and expects that refused, and reads right after a write), and a
tenant server refuses to start on a store that fails. Listing does not have
to be consistent: it is used only by cleanup and to rebuild the directory,
where a late answer leaves garbage a little longer. DigitalOcean Spaces
matters because the project's own cluster runs there; if it fails the probe,
a MinIO or R2 bucket is the fallback (see
[open questions](#open-questions-for-the-owner)).

## Serving search from object storage

### What a query reads

Cold means nothing of the database is cached on the node or in the browser
except, where noted, its hot cache. Round trips are sequential steps; within
a step, every segment's and every term's reads go out in parallel.

| query | step 1 | step 2 | step 3 | round trips cold |
|---|---|---|---|---|
| a row by primary key | the key index block of each segment (or none: keys are kept on the node, as cold segments do today) | the doc store block holding the row | | 2 (1 on a node) |
| BM25 top k over a text field | the dictionary block of each query term | each term's postings with their block maximums, and the field's lengths | the doc store blocks of the k hits | 3 (2 with the dictionary in the hot cache) |
| text with a keyword filter | as above, with the filter value's entry | as above, with the filter's postings | as above | 3 |
| IVF vector top k | the nearest centroids are in the hot cache: the chosen clusters' docIDs and codes | the float32 vectors of the candidates, to re-rank | the doc store blocks of the k hits | 3 (2 without re-ranking) |
| hybrid (BM25 and vector, fused) | both of the above, side by side | | | 3 |
| HNSW vector top k | one read per hop through the graph | | | tens: **not for this mode** |
| `GROUP BY` and aggregates over columns | the columns' blocks, pruned by zone maps in the hot cache | | | 1 to 2, with bytes in proportion to the rows scanned |
| a graph walk | one step per hop | | | one per hop |

A whole packed tenant is fetched in one GET when it is opened, after which
nothing in the table goes to the store.

One caveat on step 2: a very common term's postings in a large segment can
be megabytes. They are fetched in parallel ranges (more bytes, the same
round trip), or in two steps for top k: the block maximums first, then only
the blocks that can still reach the top k (fewer bytes, one more round
trip). The planner picks by size, and M0 measures where the line is.

### The hot cache

Every base of a spread database gets a hot cache object: the meta slot or
manifest, each segment's header and section directory, the index over each
dictionary's blocks (and whole dictionaries under a size limit), IVF
centroids, column zone maps, the primary-key index, and the doc store's
block index. It is what a node or browser reads first and keeps: typically
a small fraction of the database (how small is one of M0's measurements).
It holds nothing the base does not,
so its format can change freely: a node that finds an older version rebuilds
it from the base.

### What changes in the engine for it

- **Range reads at the chunk, not the section.** Cold segments today fetch a
  whole section the first time a query touches it (A10). Modes B and C fetch
  the chunks a read needs. Chunks are 256 KiB by default; the chunk size is
  per segment (`ColdRef::chunk`), so published images can use 64 KiB without
  a format change.
- **IVF as the default vector index for spread and published bases.** HNSW
  stays for data held on a node's local cache.
- **Larger, fewer segments in published images.** Each segment multiplies the
  requests of every step. `chloedb publish` merges to a few segments first.
- **Fetching ahead by plan.** The planner knows, before it starts, which
  sections and blocks steps 1 and 2 need; it asks for them together rather
  than faulting them in one page at a time.

### Latency

The model: a cold query costs its sequential round trips times the store's
latency for a small range read, plus the time to move its bytes. The store's
latency is the term that varies:

| where the bytes come from | per round trip | documented as |
|---|---|---|
| S3 Standard, from a node in the same region | AWS's guidance says 100–200 ms; often lower in practice, which M0 measures | "consistent small object latencies (and first-byte-out latencies for larger objects) of roughly 100–200 milliseconds" ([AWS](https://docs.aws.amazon.com/AmazonS3/latest/userguide/optimizing-performance.html)) |
| S3 Express One Zone, same zone | a few ms | "consistent single-digit millisecond data access" ([AWS](https://aws.amazon.com/blogs/aws/up-to-85-price-reductions-for-amazon-s3-express-one-zone)) |
| a CDN edge, from a browser | depends on the user's network: tens of ms on a good connection | |
| the node's NVMe cache | a fraction of a millisecond | |

Which gives, for a cold three-step query, **estimates** that M0 has to
replace with measurements:

| mode and store | estimate |
|---|---|
| A or B on S3 Express One Zone | 15 to 30 ms |
| A or B on S3 Standard, at 20 to 40 ms a round trip | 60 to 150 ms |
| A or B on S3 Standard, at AWS's 100 to 200 ms | 300 to 600 ms |
| C from a CDN, first query (hot cache plus three steps, plus starting the WASM module) | a few hundred ms |
| any mode, once the blocks are cached | about what the same query takes on a local file today |

Opening a tenant adds its own two round trips (one with a right hint)
before the first query, and for a packed tenant the query then reads
nothing more from the store. So the audit's target (cold open plus first
query under 100 ms at the median) is plausible for packed tenants on MinIO
on the same machine or on S3 Express, and on S3 Standard only if its round
trips come in at tens of milliseconds. M0 measures it before any format is
frozen.

### Cost

S3 list prices in us-east-1, to be checked when the numbers are used:

| | S3 Standard | S3 Express One Zone (since 10 April 2025) |
|---|---|---|
| storage, per GB-month | $0.023 | $0.11 |
| PUT, per 1,000 | $0.005 | $0.00113 |
| GET, per 1,000 | $0.0004 | $0.00003 |
| data, per GB | none within the region | $0.0032 uploaded, $0.0006 retrieved |

Worked examples (arithmetic from the prices above, not measurements):

- **A cold query** of three terms over four segments with ten results makes
  about 4 × (3 + 3 + 1) + 10 = 38 GETs: about $15 per million cold queries on
  S3 Standard, about $1 on Express plus its per-GB charge. Queries served from
  a node's cache cost nothing in requests; the node is the cost.
- **Storing ten thousand tenants of 10 MB** (100 GB): about $2.30 a month on
  S3 Standard.
- **Writes.** Each group commit is one PUT of `HEAD`, plus one for each
  256 KiB of log sealed. A tenant that commits once a second all month makes
  2.6 million PUTs, about $13 on S3 Standard; an agent that commits a
  thousand times a day makes 30,000, about $0.15. A tenant that writes
  constantly is cheaper on Express, or in a cluster's shard.
- **Following a tenant** by asking once a second whether `HEAD` changed is
  2.6 million GETs a month, about $1 on S3 Standard.
- **Limits.** S3 allows at least 3,500 PUTs and 5,500 GETs a second per
  prefix, and each tenant is its own prefix, so a fleet's rate is not capped
  by the bucket.

A comparison with turbopuffer's and S3 Vectors' list prices, which the
audit's demo calls for, is left to M0, from their pages on the day it is
written.

### The browser (mode C)

`chloedb publish shop.chloedb --to s3://bucket/search/` writes a
read-optimised image (few segments, IVF, 64 KiB chunks) and its hot cache
under names that include a content hash, so they can be cached forever, and a
small `latest.json` naming them, cached for a minute. A page loads the WASM
module in a Web Worker, opens the image by URL, and queries it with SQL.

What the WASM build needs that the engine does not have today:

- **No `mmap`, `flock` or threads.** The single-file layout is read through
  a fetch-backed page cache instead of a mapping (the `segment::Fetch` trait
  cold segments use is the seam). The build is read-only and needs no locks.
  The merger and background threads are compiled out.
- **Synchronous reads from an asynchronous browser.** The engine reads
  synchronously. In a Web Worker, a synchronous `XMLHttpRequest` with a
  `Range` header is allowed and needs no special headers on the host (the
  approach `sql.js-httpvfs` took for SQLite). `SharedArrayBuffer` with
  `Atomics.wait` is faster but needs cross-origin isolation headers, which
  GitHub Pages does not send.
- **Scalar and `simd128` paths** for the vector kernels, beside AVX-512 and
  NEON.
- **Query vectors.** A text query needs an embedding. A static embedding
  model (a table of vectors per token, being added in another thread) runs in
  WASM in microseconds; a transformer model does not belong in this mode.
- **The host.** Any static host that answers `Range` requests: S3, a CDN in
  front of it, GitHub Pages. Cross-origin use needs CORS that allows `Range`
  and exposes `Content-Range`. S3 serves one range per request, so each
  block is a request; HTTP/2 to a CDN makes that cheap. An image kept in a
  Git repository for GitHub Pages is bound by GitHub's limit of 100 MB a
  file.

What it cannot do: access control below the file (whoever can fetch the image
can read all of it; per-user data needs per-user images or signed URLs), and
writes.

## Tenant servers

### Routing

Each tenant has one preferred node, by rendezvous hashing of its id over the
live tenant servers. The list of live servers comes from 0.6.0's metastore
when the fleet runs beside a cluster, or from a Kubernetes headless Service
or a static `--tenant-peers` list otherwise. A request that reaches another
node is forwarded; served anyway, it would still be correct, because the
store decides who writes. When the node list changes, tenants move to their
new preferred nodes as they are next used.

### Lifecycle

```text
 absent ──create──► open (writer) ──idle 5 min──► asleep ──request──► open
                        │                            │
                        └──────────── delete ────────┴──► deleting ──► absent
```

- **Create** is one conditional put of `HEAD`, plus the directory row.
- **Open** is the two round trips above. The template check happens when
  the tenant is first written.
- **Asleep**: the node makes a base if the log has grown since the last one,
  closes the database, and keeps its local copy on disk as a cache (bounded by
  `--tenant-cache-gb`, least recently used first). A sleeping tenant costs
  its storage and nothing else.
- **Quotas** per tenant, in the directory: bytes, rows, open time, queries a
  second, writes a second. A tenant over its quota is refused with 429 and
  the quota named.

### Isolation

Tenants share a process. Each open tenant gets its own memory account, which
has to be built (today the memory budget is one per process), and every
query a deadline, so one tenant cannot exhaust a node; a tenant that goes
over is closed and reported. Process
isolation per tenant was considered and left out: it costs a process per
open tenant and the threat (a tenant's SQL reading another's data) is
handled by routing every request to exactly one database by its key's
scope.

### API

```text
POST   /v1/tenants                       {"id", "template"}           create
GET    /v1/tenants?prefix=&state=        list (from the directory)
DELETE /v1/tenants/<id>                  delete
POST   /v1/t/<id>/query | /write | /sql  as /v1/query, /v1/write, /v1/sql on one database
GET    /v1/t/<id>/mcp                    the MCP endpoint, scoped to the tenant
POST   /v1/t/<id>/export                 a single-file copy, as a checkpoint
POST   /v1/tenants/import                {"id", "url"}: a .chloedb file becomes a tenant (uploaded as its packed base)
```

Keys are scoped to a tenant or a prefix of tenant ids, using 0.5.0's tenant
tokens; an admin key of the fleet manages tenants but its requests to a
tenant are logged as such.

### Writes and reads

- **Write latency** is one conditional PUT after the group-commit window:
  10 ms plus the store's PUT latency.
- **Throughput per tenant** is bounded by group commits, one at a time: at
  25 ms a PUT, a tenant commits 40 groups a second, each holding as many
  transactions as arrived. Thousands of rows a second per tenant are
  reachable; that is far above what an agent writes, and the reason a busier
  table belongs in a cluster.
- **Read levels.** `local` (the default): the node answers from what it
  holds. On the tenant's writer that includes every write it acknowledged; on
  a node that was replaced as writer without knowing, or on a follower, it
  can be behind. `strong`: before answering, the node asks the store whether
  `HEAD` is still the version it holds (one conditional GET, shared by the
  reads waiting at that moment) and catches up if not, so the answer
  includes every write acknowledged before the read began.
- **Followers.** A hot tenant's reads can be spread over several nodes. They
  open it read-only and ask whether `HEAD` changed at an interval they
  choose; a change brings the new tail in the same answer, which they apply
  as a replica does. The writer's node can also nudge them.

## The blackboard

The audit's product direction 2: a shared store for many agents working one
job, from any vendor, through MCP. It is a tenant made from the template
`blackboard`:

```sql
CREATE TABLE tasks (
  id KEYWORD PRIMARY KEY, title TEXT, spec TEXT,
  state KEYWORD,            -- open, claimed, done, failed
  owner KEYWORD, lease_until TIMESTAMP, attempts INT, result TEXT,
  emb VECTOR(256)
);
CREATE TABLE findings (
  id KEYWORD PRIMARY KEY, task KEYWORD, agent KEYWORD, body TEXT,
  emb VECTOR(256), dup_of KEYWORD, ts TIMESTAMP
);
CREATE TABLE events (
  id KEYWORD PRIMARY KEY, ts TIMESTAMP, agent KEYWORD, kind KEYWORD, ref KEYWORD, body TEXT
);
```

Its MCP tools:

| tool | does |
|---|---|
| `claim(n, lease_s)` | gives the caller up to `n` open tasks, or claimed ones whose lease has passed, in one transaction on the tenant's writer; returns them with their leases |
| `heartbeat(task)` | extends the caller's lease, refused if the lease passed to another |
| `complete(task, result)` / `fail(task, why)` | ends the caller's claim |
| `post(body, task?)` | searches `findings` for one of the same meaning first (vector and text, above a threshold) and records the new one as a duplicate of it if found |
| `search(q)`, `timeline(since)` | hybrid search over findings and tasks; the events in order |

Why it holds: every commit to one tenant is ordered by `HEAD`, so two agents
claiming the same task are ordered and only one wins, even if two nodes
briefly both serve the tenant; a node that dies after acknowledging has its
writes in `HEAD`; a node that dies before cannot have acknowledged; an agent
that retries after a timeout carries an idempotency key, so its post or
claim is applied once. A task lease is a time the agents compare with the
server's clock, so a claim can pass to another agent while a slow one still
works; `complete` from the slow one is then refused, which is what makes the
task done once. The audit's demo, fifty
headless workers on mixed vendors migrating a codebase through one
blackboard with workers killed at random, is milestone M5's test: no task
done twice, duplicates merged, the timeline replayable.

## ChloeCtx

A ChloeCtx project store is one ChloeDB database already. As a tenant, it can
be kept on the team's bucket instead of one laptop: `chloectx sync --to
s3://…` uploads it as a packed base and its log after, and teammates' Claude
Code sessions open it read-only as followers. That is the "sync as real
replication" of 0.4.0 on this layout, and a separate design.

## Failure modes

| failure | what happens | what the user sees |
|---|---|---|
| A node dies with a group not yet committed | those writes were never acknowledged; clients retry | an error, then success on retry |
| A node dies after committing a group, before answering | the writes are in `HEAD`; the retry carries the same idempotency key and is not applied twice | success on retry |
| A commit times out and the node cannot tell | it answers "in doubt" and reloads; the retry's idempotency key settles it | a retry inside the client library |
| Two nodes write one tenant (a routing change, a pause of any length) | each commit is conditional on the one before, so the node holding the older `HEAD` is refused and reloads | `NOT_WRITER`, retried by the client library |
| A replaced writer keeps uploading segments or logs | their names carry its old epoch, so they overwrite nothing and `HEAD` never names them; cleanup removes them | nothing |
| A node replaced as writer serves a read before it finds out | under `local`, it may miss writes acknowledged by the new writer; under `strong` it cannot | choose `strong` where that matters |
| A tenant is deleted and created again under the same id | a new incarnation: the old one's objects are never read, and a writer of the old one is refused | nothing |
| The store is down | open tenants keep serving reads from the node's copy; writes fail (503); closed tenants cannot open | 503 naming the store |
| The store is slow | write latency rises with it; reads served from caches do not | the latency metrics, per tenant |
| A base upload is cut off | `HEAD` points at a base only after it is uploaded, so a cut leaves unnamed objects and the previous base | nothing; cleanup removes them |
| A reader holds an old base past its retention | it gets a 404, reads `HEAD` again and reopens | a slower query |
| A store without conditional puts, or whose reads can be stale | the probe fails at start, and the server refuses to run on it | an error naming the missing guarantee |
| The directory is lost or wrong | tenants still open from their prefix; `tenants rebuild` lists the root | slower opens until rebuilt |
| One tenant is too hot for one node | followers take its reads; its writes stay on one node | the tenant's metrics; advice to move it to a cluster if writes are the cause |
| A tenant grows huge | it is spread at its next base; merges run on its node | nothing |
| Damaged object | every object is checked against its crc (`HEAD`'s, the `.crc` tables, `STRARC01`'s footer, the image's own checksums) before use | an error naming the object; an older kept base is opened only on request (`recover`), since it would drop acknowledged writes |
| `HEAD` grows | the tail is sealed at 256 KiB and `kept` is bounded by retention, so `HEAD` stays under a megabyte | nothing |
| A browser fetches a half-published image | names are content hashes and `latest.json` changes last | nothing |

## Migration and compatibility

Everything here is new and opt-in. No existing file changes, and an object
tenant exported with `/export` is an ordinary `.chloedb` file that any
version with the same features opens.

- A single file becomes a tenant with `POST /v1/tenants/import` (uploaded as
  its packed base, then `HEAD` created) or
  `chloedb tenants import file.chloedb s3://…/<id>`.
- The cold tier (`--cold-store`) stays for servers' own databases. Its
  segment objects and `.crc` tables are the same format the object layout
  uses, so a later version can move such a database to the object layout
  without rewriting segments.
- The manifest of a spread base declares the feature `object_layout`, so
  versions without it refuse it by name, as `cold_segments` does today.
- The fix for two `cp` copies of a directory sharing one cold prefix (A10)
  comes with this: object keys are under the tenant's incarnation, not the
  database's id.

## Alternatives considered

| option | for | against | verdict |
|---|---|---|---|
| Tenants as rows of shared tables, with a tenant column and tenant tokens | no new layout; cheap tenants | isolation is a `WHERE` the server must never forget; deleting a tenant is a delete of rows; one tenant's data shapes everyone's statistics and merges | no, for the product; still the right answer for a few hundred tiny tenants inside one app |
| A file per tenant on the local disks of a cluster's shards | today's machinery, replication included | no scale to zero, disks sized for the peak, a copy on three machines for an idle file | no |
| A writer holding a lease, with a local WAL replicated to other nodes (as Neon's safekeepers do) | write latency of a local disk | a consensus service per fleet, and the hard part of a database again | not now; the path for a "hot tenant" tier later |
| One log object per node holding many tenants' commits | far fewer PUTs for many small writers | loses the store's per-tenant fence, so it needs a lease service; a tenant's log is scattered | not now; revisit if PUT cost dominates in practice |
| Commit by creating the next log object only if it is absent, with no mutable object at all (the first draft of this design) | nothing is ever replaced; conditional create is the more widely supported condition | cleanup must delete old log objects, and a name that was deleted can be created again: a writer paused for longer than the retention could create it, be told it succeeded, and acknowledge a write nobody will ever read. Safety would rest on a pause never outlasting a timer | no: one `HEAD`, replaced conditionally |
| S3 Express append | lower write latency | one store, one class | an option per store later |
| Lance or Parquet as the format | object-storage-native formats | a second format beside ChloeDB's, and none of its indexes | no |

## What is built

A first slice of M1, as an experiment (`layout: 0`, which a later version
may refuse to read): `chloedb::tenant` in the engine, and admin-only routes
in `chloedb-server --tenants URL` ([docs](../chloedb/tenants.md)). Nothing
uses it unless asked.

| built | not built |
|---|---|
| Conditional puts and listing on `ObjectStore`: the directory store, and S3 through `object_store` (compiled, not yet run against a real bucket) | The store probe (`chloedb tenants check-store`), and any run on S3, R2, MinIO or DigitalOcean Spaces |
| `HEAD` (`STRHEAD1`: a JSON header, the tail as `STRARC01`, a crc32) and the `STRARC01` log object | `db_id` and `template` in `HEAD`; the format is not frozen |
| The commit protocol above: becoming the writer, committing by replacing `HEAD`, a refused writer reloading, an unanswered put settled | Group commit: a write is one put, and one handle's writes wait for each other |
| Packed bases, sealed logs at 256 KiB, a new base after 4 MiB or 1,000 transactions or on request, `kept`, and cleanup of what `HEAD` no longer names | Spread bases, range reads, the hot cache, IVF defaults (M2); `AS OF` from `kept` |
| Opening from an empty cache, reusing a cached base, following another node's commits | Fetching logs together with the base; reusing the working copy across restarts (the base is copied and the logs replayed at each load) |
| Creating (put if absent), deleting (`HEAD` first) | The fleet-wide sweep of leftover incarnations; batched deletes |
| `POST /v1/admin/tenants`, `/v1/admin/tenants/:id`, `…/sql`, `…/base`, with an admin key | The tenant API of this design (`/v1/tenants`, `/v1/t/<id>/…`), tenant keys, routing, the directory, idle closing, quotas, templates, the blackboard, the browser build |

Tests (`chloedb/tests/tenant.rs`, on a directory store): two nodes writing
one tenant, four nodes writing at once (every acknowledged write present,
every refused one absent), a writer that slept through another's bases and
cleanup, delete and create again, a store that fails before or after it
took a put, and a damaged `HEAD`. The simulator's model of the store and
the crash tests of M1's gate are not written.

One thing the code changed in this design: step 2 of the commit protocol
first read "the same put raises `epoch`"; a node now takes the epoch with a
put of its own before it uploads under it.

## Open questions for the owner

1. **Is the blackboard the first product**, or is it per-customer retrieval
   (the audit's direction 7) with the blackboard after?
2. **Which stores to support at launch.** AWS S3, GCS, Azure, R2 and MinIO
   document the conditional puts the design needs. Does DigitalOcean Spaces?
   If not, is a MinIO or R2 bucket acceptable for the project's own fleet?
3. **The packed threshold, the group-commit window and the tail's size**
   (32 MiB, 10 ms and 256 KiB proposed) are guesses until M0. Agree to fix
   them from its numbers.
4. **Where the directory lives**: in a cluster's table (proposed when a
   cluster exists), or in a tenant of its own for fleets without one?
5. **The word.** "Tenant" in the API, "space" as ChloeCtx says, or "agent
   file"? The API name is hard to change later.
6. **Is the WASM build part of 0.7.0's gate**, or 0.7.x?
7. **Tenant-scoped keys** depend on 0.5.0's tenant tokens. If 0.5.0 changes,
   this API changes with it.
8. **A shared-storage cluster** (shards whose data is in the object layout)
   is a natural next step. Should 0.7.0 leave room for it explicitly, or stay
   about tenants?

| door | what changes | can it be undone |
