Benchmarks

First overall when one system has to do it all

Applications rarely need one kind of query. They need full text, filters, facets, key lookups, SQL, vectors and the fusion of text and vectors, over data that keeps changing. So we test all of them at once: Strata against thirteen search engines and databases on fourteen kinds of query, at 1M and 10M documents, on a laptop and in the cloud; against SQLite, DuckDB, LanceDB and Tantivy inside an app; and against four graph databases. Strata finishes first overall in each of these comparisons. It is not the fastest at everything, and this page says where it is not.

Updated 4 November 2026 · measured, never edited · raw results linked from every page

Faster hybrid search than SQLite, DuckDB or LanceDB on every BEIR collection tested, with nDCG@10 within 0.02 of the best; 1.9× is Strata held to one thread.

At a glance

Strata's place on every kind of query

Each column is one comparison; each cell is Strata's place on one kind of query among the engines in it. The pattern repeats: first or close to it on vectors, hybrids, filtered vectors and facets; mid-table to near the top on full text; behind the specialists on typo-tolerant search, SQL aggregates and key lookups. No other engine is in the top half as often.

Where Strata loses

Where another system is clearly faster

Each report lists its losses beside its wins. These are the large ones, and what is being done about each.

Typo-tolerant search

10M, cloud · median 824 ms
Elasticsearch 32.7, OpenSearch 45.3
1M, cloud · 120 ms, Typesense 6.54

A misspelt word was expanded against the whole term dictionary, and a cluster walked it twice. Since fixed on main (#242): a faster walk and a frequency-aware 'auto' cut a coordinator's median typed query from 112 to 15.8 ms on a Xeon VM. Neither cloud run had it, and the engines have not been compared again with it.

SQL aggregates

10M, cloud · 4,274 ms
OpenSearch 4.86, Elasticsearch 7.75
1M, cloud · 178 ms, OpenSearch 4.29
No server · 881 ms, DuckDB 10.1

A GROUP BY with HAVING over a filtered table: Strata's largest loss, and it grows with the data. Elasticsearch and OpenSearch answer it from doc-value aggregations, DuckDB with its vectorised column engine. Inside an app Strata's aggregates are 2 to 4 times faster than SQLite's and 11 to 87 times slower than DuckDB's. Not fixed yet.

BM25 under load

10M, cloud · 16 clients 493 q/s
OpenSearch 777, Elasticsearch 608
1M, cloud · 1,128 q/s, Qdrant 2,276

Every BM25 query through a coordinator took two rounds to the shards: term statistics, then the query. At one client Strata is level with OpenSearch at 10M (4.36 against 4.32 ms). Fixed after both runs (#245): the coordinator keeps each shard version's statistics, +51% at 16 clients in a container (1,026 to 1,547 q/s), same answers. A cloud re-run is in progress.

Key lookups

10M, cloud · 0.86 ms, 5th of 9
Postgres 0.37, Weaviate 0.39
1M, cloud · 1.30 ms, 10th of 14

At 10M every engine used its own read by id, Strata its key API, and Postgres, Weaviate, ParadeDB and Qdrant answered in about half Strata's time. The 1M run sent Strata's lookup as SQL through the query planner. Inside an app a read by key takes 21 µs, and SQLite's read by row id 8 µs.

Vector recall at the shared settings

10M, cloud · recall@10 0.795
Qdrant 0.941, Postgres 0.826
1M, cloud · 0.801, Qdrant 0.901

Every engine gets HNSW with m 16, ef_construction 200 and a search list of 64. Strata scores 8-bit codes and re-scores the best 40 with full vectors, so its vector speeds are measured at this recall: read the two together. Inside an app, at its defaults, Strata's similar-items recall is 0.996.

Single-row writes inside an app

No server · one row a commit 4,022/s
SQLite 5,128 (FULL), 11,091 (NORMAL)

SQLite is faster at one durable row a commit and at updating one row's price. Batches turn it around: at 1,000 rows a commit Strata takes 95,670 rows a second to SQLite's 18,905. Updating indexed text or a vector was the worst case, 60 title updates a second to SQLite's 735 (FULL). Keyed updates (#223) since raised it to 1,797 a second, measured on a newer CPU where SQLite was not run again.

A feed through a graph walk, and one-hop neighbours

No server · feed 125 ms, LanceDB 28.3
Graph · 1 hop 0.35 ms, Memgraph 0.18

The feed's personalized PageRank over a 3.7M-edge table is 108 of its 113 ms, spent resolving keys and neighbours. In-memory graph stores answer one and two hops in about half Strata's time; Strata leads on paths and PageRank.

Principles

How we keep it fair

The same resources

Every engine gets the same CPUs and memory as Kubernetes limits, on machines of its own, with the same data, text analysis and vectors.

Answers checked beside speed

Recall@10 against an exact search, and nDCG@10 where the collection has judgments. A fast wrong answer does not win.

Medians, not the best run

Three passes at 1M, and the median of each test. The cold first pass alone is not used: it penalises engines on the JVM.

Every gap shown

A kind an engine cannot run is marked and counts as last place. Paid features run on trial licences say so. Failed runs are reported, not dropped.

Load left out of the ranking

Strata's cluster shards were built offline from local files while the others took their documents over HTTP, so load times are shown but never ranked.

Open and reproducible

The scripts, settings, images, the data's SHA-256 sums and every raw report are in the repository, with the machine each number came from.

Questions

Frequently asked

Are we biased?

Probably, yes. We build Strata, we chose the query kinds and we wrote every engine's queries. To keep that in check, each engine runs at its defaults plus the tuning its own documentation recommends, every setting and request is in the method, and we audited our own runs and changed how we report them (what we found). If you know a better configuration for any engine, open an issue or a pull request and we will run it again.

Why rank by summed places instead of average speed?

Latencies differ by a thousand times between kinds of query, so an average of speeds is decided by the slowest kind. Places weigh every test the same: each engine is 1st, 2nd and so on per test, and the places add up. The per-kind tables show every place and value, so any other weighting can be read off them.

Doesn't counting a missing kind as last favour Strata?

It favours breadth, which is what a mixed workload needs, and it matters. At 1M in the cloud, on only the seven kinds every engine runs, Milvus is first, Qdrant second and Strata third; on the average place over only the tests each engine ran, Milvus, which runs 10 of the 14 kinds, leads. At 10M, Postgres, which answered 18 of the 45 tests, comes first under both rules. Each report shows its ranking under these rules beside the main one.

Why are only nine engines ranked at 10M?

Five did not run at the 1M run's 52 GiB: Typesense and Milvus ran out of memory, Meilisearch and Manticore were still loading after nine and eight hours, and Redis keeps everything in memory. Milvus and Redis then ran on a 128 GB machine with the same CPUs; their numbers are shown beside the others but not ranked, since they had twice the memory. What did not finish has the details.

Can I run it myself?

Yes. Each report links its scripts and raw results, and How we test has the commands, for one laptop or a cloud account.
