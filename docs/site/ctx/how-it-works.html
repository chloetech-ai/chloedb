How it works

Store everything, bring back only what helps

ChloeCtx is one small daemon per memory that owns a ChloeDB file, an MCP server any model can query it through, and, in Claude Code, hooks that record every session. This page follows it in Claude Code, where it is most complete. Storing is cheap and a missed record can never be recovered, so it stores everything. Loading costs the model attention, so it is gated, budgeted, and never repeats what the model can already see.

Architecture

One daemon per project owns the file

Only one process at a time may write a ChloeDB file, and hooks are short-lived processes that run alongside the MCP server. So one daemon per project owns the database, and the hooks and the MCP server are its clients over a Unix socket.

Lazy start

The first hook starts it

The first client to find no socket spawns the daemon under a lock. The 129 MB embedding table is memory-mapped rather than read, so that first hook takes 50 to 72 ms.

Many readers, one writer

Reads never wait for a write

Reads run side by side on a snapshot. One writer thread commits whatever is queued as one transaction, and merges happen on background threads.

Never in the way

Fails silent, says it once

A hook that cannot reach the daemon in time exits 0 with nothing. A daemon that cannot start is reported once, with its last words and chloectx doctor.

Records

One table, small keys, three levels

Everything is one ChloeDB table, memory. A captured event is redacted, trimmed and cut into records of at most 400 bytes. A small window matches a question better than a long chunk where the answer is one fact among many, and a context budget holds about ten of them instead of five snippets.

Notes

A small model writes down what each turn agreed

After each turn, off the prompt's path, the daemon gives the turn to a small model through claude -p, with up to 40 related notes. Seeing them is what lets it update a note written weeks ago instead of adding a near copy. It costs about $0.001 and 8 seconds a turn with a fast model.

When it matters

Each note names its situations

A later request rarely uses the words of the note it needs. "Add a settings.toml loader" shares no word with "Python 3.8", but it matches the note's When: parsing a config file.

Who said it

Only the user makes rules

Every note says whether the user stated it or the assistant found it. What the user only asked about, or an assistant's open question, is not written down as the project's.

Kept current

Replaced, done, retired, merged

A new note can replace an old one, close planned work, or retire work that was scrapped. Every eight turns related notes are merged, keeping every number, name and reason.

Notes are tied to the code they were written against

Each note keeps its commit, a hash of the files it names and the identifiers it mentions. When it is shown, ChloeCtx checks those files in the working tree.

The live window

Never repeat what the model can still see

For each session the daemon keeps where its context window starts: the session's start, or its last compaction. Every recall query leaves out the session's records from there on, and anything already injected since. A compaction moves the start, so exact details its summary dropped become findable again.

exclude { r : r.session = s ∧ r.seq ≥ ws } ∪ injecteds
A session, step by step

Three push points and one pull path

The briefing at the start, recall with each prompt, and notes before an edit come without the model asking. The memory tools are there when it does.

Ranking

Words and meaning, then gentle priors

BM25 and vector search each return their top 50 outside the live window. Their scores are normalised over the union and blended. Priors for the kind of record and its recency break near ties without overriding relevance.

Routine work is pushed down: a passing test run or an empty tool answer matches any question about its turn and says nothing. Packing is greedy: at most twelve records, eight per turn, each line carrying its kind, session, turn, age and id, so the model can open it with memory_timeline.

rel(r) = w·bm25̂(r) + (1 − w)·coŝ(r)
S(r) = rel(r)·(1 + λι·ι(r)) + λt·e−(seqmax − seq(r))/τ

ι is the kind's prior, from 1.0 for a rule the user stated to 0.3 for tool output. Before the main search, up to four notes that match the prompt on their own (cosine ≥ 0.40 or weighted term coverage ≥ 0.30) are shown without the gate.

The gate

Full, brief, or nothing at all

Normalised scores cannot gate, because the best candidate always scores 1. The gate reads absolute evidence instead: the highest cosine and term coverage in the top five, how far the best scores stand above the tenth, whether BM25 and vectors agree on the top record, and whether the prompt refers back ("we decided", "last time").

Its weights come from a logistic fit on LongMemEval-S. The upper threshold holds precision 0.9 on the fit, the lower one 0.7. It is the weakest part of the design, and the benchmarks say why.

The query engine

Connect a request to what it implies

Search finds records that look like the request. Some requests depend on something they never name. The query engine has a small model plan several typed searches, fuses what they return, and has a second call pick the records that matter. It runs in the background while Claude starts working, and its picks arrive with the next tool result.

  1. 1 · PlanTyped searches

    The planner turns the request into searches by meaning, by words, by kind and by date, such as "the school's rules" for an order.

  2. 2 · SearchAll at once

    Each runs on the same snapshot, side by side, with ChloeDB's filters on session, file, kind and time.

  3. 3 · FuseOne list

    Results are fused by rank, and the best of them go to the ranker with their context.

  4. 4 · PickWhat matters

    A second call picks the records that change the answer, including stated tastes when a request asks for advice.

Errors and fixes

A failure that passed is remembered as a fix

When a command fails and later passes, with edits or other commands between, ChloeCtx writes down the error, the steps that changed something, and what showed it fixed. cd x && cargo test 2>&1 | tail counts as cargo test. When the same error comes back in any session of the project, its fixes come with it, at most two, once a session.

Stored, never pushed

Text from outside the project is data

What WebFetch, WebSearch, an MCP tool or curl and gh issue view returned is stored but never put into a prompt on its own. Search shows it fenced as quoted data, so a planted instruction never reaches a later session as "earlier work".

Branches

Worktrees share a store, not their code

A note written on a branch this worktree does not have is labelled as such, unless its files are the same here. A rule the user gave holds on every branch.
