How we test

How the numbers are taken, and how we checked ourselves

A benchmark by a database's own authors deserves suspicion, ours included. So the method is written down to each engine's request, every raw result is committed, and before publishing we audited our own runs as a skeptic would. This page has the workload, the rules, the ranking and its alternatives, what the audit found, and the commands to run it all again.

The workload

Fourteen kinds of query, the mix an application sends

One search box, one product page and one dashboard already need most of these. Every engine runs each kind with its closest native request; where it has none, the kind counts as one it cannot run.

The rules

The same resources, data and settings for every engine

Equal budgets, enforced

Kubernetes limits: 6.8 CPUs per engine in the cloud (what two 4-vCPU nodes have left after Kubernetes' own pods), 3 CPUs and 6 GiB on the laptop. Each engine is also told its budget: heaps, Postgres's buffers, Redis's and Qdrant's worker counts.

The same text analysis

Strata's chain rebuilt in the others: ASCII folding, Lucene's English stopwords, Snowball stemming, BM25 with k1 1.2 and b 0.75. The Lucene engines' top 10s share 93 to 96% of Strata's.

The same vector settings

HNSW with m 16 and ef_construction 200, 64 candidates, and 8-bit codes re-scored with full vectors where an engine has them.

No result caches

Solr's query result cache is off, and Elasticsearch and OpenSearch get request_cache=false. Every answer is recorded and checked.

Pinned versions

Each engine's image is pinned by tag, every Strata build is a commit on main, and the data is checked against SHA-256 sums on every node.

Defaults, plus the documented tuning

Each engine runs at its defaults plus what its own documentation recommends for the job. Every setting is committed beside the results.

What is measured

Latency, throughput and the answers themselves

  • Latency: the median and 99th percentile at one client, from request to whole answer at the client.
  • Throughput: queries a second at 4 and 16 clients. Each cell runs for 6 seconds over 300 queries, after a warm-up: one round at 1M, and at 10M rounds until two rounds' medians agree within 10%.
  • Passes: three in a row at 1M, and the median of each test is reported. The first pass alone is not used: it is the slowest of the three for the JVM engines in about 80% of cells, while Strata's equals its median. The 10M run is one pass after that longer warm-up; a second Strata on other nodes landed within 4.5% of it at the median.
  • Quality: recall@10 against an exact vector search, and nDCG@10 where the collection has judgments (BEIR NQ, and the five BEIR collections without a server). The MS MARCO slices have no judgments of their own.
  • Writes: single and batched inserts and updates at 16 clients, and how long until a written document is found by a search.
  • Streams: a Redpanda topic at rising rates, then flat out, then a consumer that crashes before committing its offsets; events written twice and events lost are counted.
The ranking

Summed places, and the same ranking under other rules

Latencies differ a thousand times between kinds, so an average of speeds would be decided by the slowest kind. Places weigh every test the same. Each of the 14 kinds gives three tests (median and 99th-percentile latency at 1 client, queries a second at 4 clients) and the three vector kinds a recall test: 45 in all. Each engine takes its place on each test and the places add up; a kind it cannot run counts as last place. Load time and size are left out, because Strata's cluster shards are built offline while the others take their documents over HTTP.

What changes the order

At 1M in the cloud, Strata stays first with throughput at 16 clients instead of 4, and with gaps under 15% counted as ties. It is not first on only the seven kinds every engine runs (Milvus, then Qdrant, then Strata), nor on the average place over only the tests each engine ran (Milvus). Its overall lead is breadth: no engine that runs every kind runs them as well. At 10M the same holds, with Postgres first on the common kinds and on its average place, after its text kinds were stopped at a 20 s limit.

Where to check it

Each cluster report has the ranking under all five rules, generated from its raw results by the site's data script, and every place and value per kind. The reports' own rank.md, from deploy/compare/rank.py, also ranks load (47 tests).

Run it yourself

Every run is a script in the repository

A laptop cluster (kind), one engine at a time
cd strata-server
deploy/kind-test.sh up
deploy/compare/compare.sh image
deploy/compare/compare.sh up es
deploy/compare/compare.sh load es
deploy/compare/compare.sh run es
deploy/compare/compare.sh down es
Every engine on DigitalOcean, at once
cd strata-server
IMAGE=ghcr.io/chloetech-ai/strata-server:<sha> \
  BUDGET=30 deploy/compare/fanout.sh run
deploy/compare/fanout.sh analyze results/
deploy/compare/fanout.sh down
No server, on one DigitalOcean node
cd strata-py/bench/laptop
./do_part_a.sh up && ./do_part_a.sh push
./do_part_a.sh setup && ./do_part_a.sh prep
./do_part_a.sh run
./do_part_a.sh fetch results/ && ./do_part_a.sh down
These pages' numbers
python3 docs/site/scripts/bench_data.py

The full steps, budgets and costs are in deploy/compare/README.md and each report's README. If you think an engine is set up badly, open an issue with the setting you would use and we will run it again.
