Under the hood

Why Strata is fast, and why it bends

Strata does less work per query by construction. Every index is read in place from one memory-mapped file. Posting lists, columns and vector codes are laid out for the CPU's words and SIMD units. Top-k loops carry exact bounds and skip what cannot rank. A planner decides, per segment and from exact counts, which index answers each part of a statement. This page walks through those structures and algorithms, links each one to its code, and quotes only measured numbers.

The short answer

Four habits, applied to every index

Read in place, never deserialise

Opening maps the file and reads its manifest. Every index is a view of bytes in the mapping, aligned so the CPU can use them where they lie, and the kernel is told which sections are read at random.

Compress for the CPU, not only the disk

Long posting lists keep their dense parts as bitmaps on a shared word grid, so AND and OR work 64 documents at a time. Columns are bit-packed in SIMD lanes. Vectors are scored as 8-bit codes with integer dot-product instructions.

Skip what cannot make the top k

Exact score bounds per list and per block, zone maps per block and per 4,096 rows, error bounds per vector code, and Bloom filters per segment let each loop skip work it can prove useless.

Plan per segment from exact counts

Document frequencies, list lengths and histogram buckets are exact, not sampled. A vector filter's selectivity is measured near the query, where it matters, before the plan is chosen.

A query's path

From SQL to rows in six steps

Every statement takes the same path, in one process or on each shard of a cluster. Planning happens per segment, so a small fresh segment and a large merged one can answer the same statement in different ways.

    SQL with search functions, read by sqlparser and a MATCH grammar. A SELECT seen before, with new parameters, skips parsing.

Storage

One file of immutable segments, read in place

B-trees updated in place do not suit compressed posting lists, bit-packed columns or vector graphs: the best encodings are chosen per whole list. So every index lives in immutable segments, written once and merged in the background, as Lucene, Tantivy and SQLite's own FTS5 store theirs. Strata uses that design for the whole table, in one file of 4 KiB pages plus a write-ahead log.

Commits by shadow paging

A commit writes new extents, syncs them, then writes the other meta slot (transaction id, manifest location, CRC32) and syncs it. Nothing reachable from a valid slot is ever overwritten, as in LMDB, so there is no rollback journal: a torn meta write fails its checksum and the other slot still names the last whole state. Small transactions append to the WAL instead and sync once per commit.

MeasuredA durable one-row commit takes 4.1 ms at the median, nearly all of it macOS's F_FULLFSYNC; with 1,000 rows a transaction the WAL takes 98,000 rows a second.M2 · results

storage/pager.rsstorage/wal.rs

Sections the CPU uses where they lie

A segment is a directory of named sections, each with its offset, length and CRC32. Sections start on 64-byte boundaries, and on page boundaries once they pass 4 KiB, so a &[u64] view taken straight from the mapping is aligned and nothing is copied or decoded to open an index. Readers open per field, so a query touches only the headers of the fields it uses, and a section's checksum is checked the first time a query reads it.

MeasuredOpening a database cold takes 6.8 ms with 10 segments and 40 ms with 100.M2 · results

segment/mod.rs

A page-cache hint per section

The sections read at random positions (dictionaries, the HNSW graph and its codes, float32 rows for reranking, the doc store, the key index, graph edges) are advised MADV_RANDOM, so a cold page fault reads one page instead of the kernel's read-around. Postings, document lengths, columns and IVF clusters, which are read a run at a time, keep read-ahead. An HNSW search also prefetches each hop's neighbours before it scores them.

MeasuredA cold HNSW query on Quora reads 9,672 pages (136 ms) with the kernel's default, 4,836 pages (113 ms) with the graph and codes advised random, and takes 28 ms with each hop's neighbours prefetched.M2, 16 KiB pages · results

segment/mod.rs · random_accessvector/hnsw.rs · prefetch

Snapshots by reference count

A snapshot is an immutable version of the manifest: its segments, their delete sets and the collection's statistics. Readers pin one, and the writer publishes the next, so a reader never waits for the writer and always sees one consistent version, across every table of the file.

MeasuredTaking a snapshot costs at most 0.13 µs.M2 · results

storage/snapshot.rs

New rows searchable at once, indexed when asked

Committed rows go to a memtable of 1,024-row chunks. A full chunk is built once as a small in-memory segment; the last one is built only when a query needs its indexes, at most once per change, and shared by every snapshot of that change. So a commit indexes nothing, queries see it at once, and the memtable needs no index code of its own: it is read by the same operators as any segment.

MeasuredThe first query after a write rebuilds the last chunk with every index of the table in 17 to 20 ms, against 169 ms for an unchunked memtable of 10,000 rows.M2 · results

Full text

dictionary, Loom lists, MaxScore

A text query spends its time in three places: finding its terms, walking their posting lists, and scoring. Each has a structure built for it.

A front-coded dictionary walked as a trie

Terms are sorted in front-coded blocks of 32 under a sparse in-memory index of each block's first term. A typo-tolerant word walks the dictionary as a trie and skips every run of terms whose start is already too many edits away: inside a block it passes terms by their stored lengths alone, and each letter's row of edits is computed for up to 63 letters at once in a machine word (Wu and Manber's bit-parallel matching, with Hyyrö's swap of two letters).

MeasuredLooking up a typed word among ORCAS's 797,472 terms takes 1.4 ms at the median with one edit and 7.8 ms with two, against 77 and 106 ms testing every term.Xeon VM, 2.10 GHz, one thread · typos

text/dict.rstext/fuzzy.rs

Loom: posting lists on a shared word grid

Lists of terms in 512 or more documents are Loom lists, a design from Strata's own posting-list study. A dynamic program cuts each list into partitions, each a bitmap, an Elias-Fano sequence or a run, and leans toward bitmaps (λ = 5/4). Bit i of any list's bitmap is docID 64⌊b/64⌋ + i, so two lists' bitmaps AND and OR word by word. A conjunction decodes the shortest list 256 candidates at a time and lets every other list, rarest first, filter that batch in place. Shorter lists use SIMD BP128 blocks.

MeasuredAgainst BP128 for every list, conjunctions are 7.6 to 11 times faster (21 against 230 µs on TREC-COVID) and the index 2 to 4% smaller. In the study, Loom is the size of partitioned Elias-Fano with 2.4 to 3.0 times faster AND and 3.8 to 7.7 times faster OR.M2 · results, the study

postings/codecs/loomtext/postings.rs

Exact bounds, then MaxScore

Every list starts with its impact frontier, the Pareto-optimal (term frequency, length) pairs of its postings: since BM25 grows with one and falls with the other, the list's best score under any parameters is the best over a handful of pairs. A block table gives each 128 postings its largest frequency and shortest length, a bound for Block-Max WAND. MaxScore, the default, lets lists whose bounds cannot lift a row past the threshold only confirm others' candidates. In a Loom list a frequency is read in O(1) from the cursor's rank, and a row's length is one byte.

MeasuredMaxScore is 1.9 to 2.6 times faster than Block-Max WAND on BEIR's queries. Warm BM25 top 10 is 1.7 to 3.2 times faster than Tantivy 0.26 on four BEIR collections (0.391 against 0.681 ms on TREC-COVID), one thread and one segment each.M2 · results

text/bm25.rstext/postings.rs · frontier

Many lists at once

A typo-tolerant word can bring up to 50 lists. Their current docIDs are compared with a candidate 16 at a time into a mask, which compiles to vector compares, and with 16 or more essential lists MaxScore adds up scores a window of 4,096 documents at a time before it consults the others. A shard reuses a snapshot's typo expansions between a coordinator's two rounds, and fuzzy => 'auto' corrects only words rare enough to be typos, weighted by a noisy channel.

MeasuredThrough a coordinator over two shards of 1M MS MARCO passages, the median typed query fell from 112 to 15.8 ms, and four clients went from 17.7 to 137 queries a second.Xeon VM, 2.10 GHz · typos

text/bm25.rs · for_each_ontext/fuzzy.rs

A filter drives or is probed

A filtered BM25 query either walks the filter's members and scores each by seeking the lists, or runs the query and skips candidates outside the filter. The choice is a fitted cost: drive when members × terms × 1.8 (0.9 for Block-Max WAND) is below the total length of the query's lists, constants fitted over selectivities from 0.01% to 30%.

MeasuredFiltered BM25 is 3.1 to 4.0 times faster than Tantivy's.M2 · results

text/bm25.rs · drive_cost

The same score in every segment and shard

BM25 uses statistics summed over the snapshot's segments, Lucene's idf and a document count of the rows that have the field, so a row scores the same whichever segment holds it. A coordinator sums its shards' term statistics the same way. A relevance gate in CI holds nDCG@10 and recall on three BEIR collections within 0.002 of committed numbers.

MeasuredStrata's BM25 is within 0.018 nDCG@10 of Tantivy's and SQLite FTS5's on four BEIR collections, so its speed is not bought with worse answers.M2 · results

Columns and keys

bit-packed blocks, zone maps, Pyramid lists

Structured fields are stored twice, each copy for a different question: a column answers "what is row d's value" in O(1), and a list per value or per range answers "which rows have it" as a set operation.

Columns in 128-row blocks

Numbers (as order-preserving keys) and keyword codes are cut into blocks of 128 rows, each stored frame-of-reference: the block's minimum, then every key minus it in the fewest bits, in the four-lane SIMD layout of BitPacker4x. A block's payload is exactly 128 × width bits, so offsets are a prefix sum and reading one row is two loads and a shift. Zone maps keep each block's and each 32-block superblock's minimum and maximum, so a range over clustered values, such as a timestamp, accepts or skips 4,096 rows per check.

forward/blocks.rs

A list per keyword value

Every keyword value also keeps a docID list, so equality and IN are set operations. Values in 64 or more rows use Pyramid, the study's speed-first design: each 65,536-docID chunk split into 256-docID blocks, each a bitmap or a few bytes, so a membership test is O(1) at any density. A per-row check reads the code column against a bitset of accepted codes instead.

MeasuredIn the study, Pyramid unites lists faster than Roaring on the clustered collection (0.355 against 0.384 ms) at 24 to 33% less space.M2 · the study

forward/keyword.rspostings/codecs/pyramid

Ranges from a histogram that also estimates

Every numeric field keeps an equi-depth histogram of 64 buckets, and each bucket is a docID list. A range is the union of the buckets it covers, plus its two boundary buckets filtered through the column. The same histogram gives the planner its selectivity, and the planner chooses per segment between this and a zone-map scan of the column.

forward/numeric.rsforward/range.rs

Facets two ways

GROUP BY a keyword reads the codes of the result's rows when the result is small, and intersects the result with each value's Pyramid list, counting only, when it is large and the values are few.

forward/keyword.rs

A read by key in a cache line

Each segment's key index is sorted 64-bit key hashes paired with docIDs, under a radix directory of the hashes' top bits (about four entries a slot), with each hash beside its docID: a lookup is one directory read and a short scan, and a cold one touches a constant number of pages. A segment of more than 4,096 keys also gets a split-block Bloom filter (12 bits a key) in memory, built on its first lookup, since a read probes segments newest first and most of them lack the key.

storage/pk.rs

Rows in compressed blocks, read for the page

Stored fields live in LZ4 blocks of 16 KiB, so fetching a row decompresses one block. Through a coordinator, a deep page or a fused score is answered by query then fetch: shards rank and send keys and scores, and only the shards holding the page's rows read their columns.

forward/store.rscluster.rs · fetch

Vectors

SQ8 and RaBitQ codes, HNSW, IVF

A vector search is mostly dot products and memory reads. Strata makes the dot products integer ones and reads float32 rows only for the candidates that can still change the answer.

Two copies of every vector

Each vector field keeps float32 rows for exact reranking and 8-bit codes for scanning, each dimension mapped onto 0 to 255 by its own range. The query's weights are quantised to int8 once, so scoring a row is an integer dot product: AVX-512 VNNI's vpdpbusd (64 byte products an instruction) on x86-64, usdot (16) on Apple silicon, four rows per query load. The kernel is picked at run time from the CPU's features, with a scalar twin as the reference in tests.

MeasuredA 1,024-dimension code scores in 14 ns with usdot (9.8 ns four at a time), against 70 ns in float32. Scoring the codes alone finds 99.8% of the exact top 10; float32 reranking settles the rest.M2 · results

vector/sq8.rsvector/kernels.rs

HNSW built and searched on codes

The graph is built on the 8-bit codes, as it is searched, so each comparison reads a byte per dimension instead of four. Searches walk fixed-degree adjacency lists in the mapped segment and rerank 40 candidates in float32 by default.

MeasuredOn Quora (522,931 vectors, 1,024 dimensions) HNSW reaches recall@10 0.990 at 0.086 ms. TREC-COVID's 171,332 vectors build in 36.6 s on codes, against 82.0 s on float32 rows, with recall@10 within 0.014 at every ef.M2 for the search · Xeon VM, one run, for the build · design

vector/hnsw.rs

Merges that keep the graph

A merge keeps the graph of its largest input that lost no rows, nodes, levels and links, and joins the other inputs' graphs to it, as Lucene 9.9 and 10.2 do: a set of nodes that covers the rest is inserted as usual, and every other node searches the bottom layer from its old neighbours, with half the beam.

MeasuredMerging four segments of 25,000 TREC-COVID vectors takes 12.2 to 12.3 s, against 37.9 s from scratch, at recall@10 0.987 to 0.989 against 0.992 to 0.993 (ef 64).Xeon VM, four threads · design

vector/hnsw.rs · join sets

IVF: one read per cluster

IVF clusters are stored back to back, each its ascending docIDs then its code rows, 64-byte aligned, so probing a cluster is one sequential read. A filter is applied by intersecting the cluster's docID list with the filter's, the same operation as a text conjunction.

MeasuredA cold IVF query on Quora takes 26 ms with read-ahead, and 10 ms with prefetching.M2 · results

vector/ivf.rs

RaBitQ: skip the float reads that cannot matter

A field can keep RaBitQ codes of 1, 2 or 4 bits a dimension instead: each row centred, turned by a fixed random rotation that spreads its energy evenly, and rounded to the grid, with two floats a row. They give an unbiased estimate of the dot product and a bound on its error, and a search reads a candidate's float32 row only if its estimate plus that bound reaches the k-th exact score found so far.

MeasuredOn FiQA (57,638 vectors, 1,024 dimensions), 2-bit codes under HNSW read 28 float32 rows a query where binary codes read 320, at recall@10 0.996 against 0.997, in 0.49 against 0.83 ms.Xeon VM, 2.80 GHz, one thread · results

The planner

Decided per segment, from exact counts

No fixed strategy wins every query. A filter can be cheap to list and costly to check or the reverse, and a vector filter that keeps 10% of the table may keep almost none of the rows near the query. The planner works per segment, from statistics the indexes answer exactly, and shows what it chose in EXPLAIN.

Materialise or probe

Each predicate is either materialised, a docID set built from postings at a cost that follows the lists, or probed, a check of each candidate against its column at a cost that follows the candidates. Estimates come from exact document frequencies, list lengths and histogram buckets; conjunctions assume independence and disjunctions use inclusion and exclusion.

query/plan.rs

Filtered vectors, measured near the query

A filtered vector search can scan the filter's rows exactly, search IVF with the filter intersected in, walk HNSW with the filter inside, or search wider and filter after. When the global selectivity leaves the choice open, the planner runs a 32-result unfiltered search and uses the share of it that passes the filter; if that finds at most one match, a 160-result sample tells a selective filter from one whose rows lie far from the query.

MeasuredOver 300 filtered vector queries, 2.7 times faster than the best fixed strategy on TREC-COVID (121 against 325 ms in total) and 6.1 times on Quora (179 against 1,089 ms), at recall@10 0.991 to 0.998 and 1.0 to 1.6 times an oracle's time.M2 · results

query/exec.rs · local_selectivityvector/cost.rs

Hybrid ranking as one plan

A fused ranking takes each input's top 100 under the same filter, rescores the union exactly with every input, and fuses them by RRF or by a weighted sum of normalised scores. Graph walks run first and hand the planner exact sets, so a vector search over a few hundred reachable rows becomes an exact scan.

MeasuredThe top-100 fusion takes 0.2 to 0.8 ms and recovers 89 to 95% of the exact fused top 10, where computing it over every row takes 0.9 to 62 ms.M2 · results

query/rank.rsquery/fusion.rs
Large plans

Search stays Strata's; joins and groups move to DataFusion

Each leaf of a plan (search, filter, ranking, a group over one table) runs on Strata's executor, so every index stays in use. When the leaves read more than 4,096 rows, the nodes above them (joins, WITH, DISTINCT, groups, sorts and windows) become one Apache DataFusion plan over Arrow batches, on the query's threads, and sorts and groups spill to disk past the query's memory budget. Hidden columns keep Strata's row order, and a plan DataFusion cannot express exactly falls back to Strata's operators with the reason.

The cluster

Shards that answer like one database

A shard is the same database file a program opens, served by strata-server. A coordinator routes, merges and hedges, and its answers match one database's: the same scores, the same order, the same facet counts.

4,096 slots under an epoch

A primary key hashes (xxh3 over a typed encoding, so the integer 5 and the text '5' differ) to one of 4,096 slots, and a slot map assigns slots to shards under an epoch. Shards refuse requests from an older map and writes for slots they do not hold, so moving slots while serving is a new map with a higher epoch. A read by key, or a query that pins its key, goes to one shard.

strata-server/src/slots.rs

BM25 in two rounds, scored as one

A BM25 query first asks every shard for its query terms' statistics, each answering from a snapshot it holds for the next round, and sums them. The query then runs on every shard with those sums, so each scores as the unsplit collection would, and the answers merge by score, ties by key. Other queries take one round; fused scores merge from each input's raw scores and are normalised over the merged candidates.

strata-server/src/coord.rsstrata/src/cluster.rs

Hedged reads

A read goes to one replica of each shard, in turn. When one has not answered within the hedge delay the next is asked too, and the first answer wins, with hedges held to a share of calls. A replica that refuses because it is full is not relieved by loading its sibling, and one that failed or was outrun is asked last for a while.

Writes and merges

Background work that stays out of the way

Reads are fast when segments are few and large, so merging matters; it must not stall writes or exhaust memory while it runs.

Flushes and merges without the lock

A flusher thread seals the memtable and its log and builds segments while writes go on; it holds the writer lock only to seal and to install. Merges, tiered by size, build their segment with no lock held, write it into reserved space, and take the lock only for a commit that carries over the deletes made meanwhile. Up to half the cores (at most four) merge at once, within half the machine's or the container's memory.

storage/db.rs · spawn_flusher, spawn_merger

Merges that stream

A merge decodes its inputs in batches of about 32 MB of image while another thread decodes the next, keeps what must see every row in compact form, and streams the image out a megabyte at a time. Past 64 MB of input it also writes its growing sections to unnamed temporary files. The bytes are the same as a build of every row at once.

MeasuredThe 2M-passage merge of the scale probe (4.5 GB of image) peaks at 4.0 to 4.1 GB of heap instead of 7.6 GB.Xeon VM, four threads · design

storage/merge.rssegment/spill.rs

Parallel builds, identical bytes

A segment of 1,024 rows or more builds on up to eight threads: fields at once, longest first; a text field analysed in runs, one per thread; its posting lists encoded in ranges of terms. The image is byte for byte that of a one-thread build.

MeasuredA TREC-COVID text segment (171,332 documents, 192 MB of text) builds in 2.9 to 3.2 s on four threads, against 9.0 to 9.7 s on one.Xeon VM · design

Why it bends

Flexible because the pieces compose

The same structures that make a query fast let one statement mix them, and let a table change shape without being rewritten.

Four index families over the same rows

A table's text, columns, vectors and graph edges are indexed together, in the same transaction. Any WHERE mixes their leaves and any ORDER BY fuses their scores, because the planner treats each as a set or a ranking with a known cost. See the queries.

query/logical.rs

Fields named by id on disk

A field is stored under an id, never by its position or name. ALTER TABLE adds a field under a new id, which older segments read as its default; drops one by leaving its id out; and renames one under the same id. No segment is rewritten, on one database, its replicas or a cluster.

storage/manifest.rsquery/ddl.rs

Fields that fill themselves

A text field can be generated from others and indexed without being stored; a vector field can name the model that embeds it from other columns as rows are written; a JSON field indexes every key by path, and its strings as text if asked.

schema.rsjson.rsembed.rs

Ranking is an expression

Any arithmetic of scores and columns, decay() by time or distance, LightGBM and XGBoost models scored bit for bit, cross-encoders, and rerank phases in a WITH, kept as versioned rank profiles beside the table.

query/rank.rsquery/model.rs

Two engines, one answer

Small results stay on Strata's operators, large ones go to DataFusion's batches, and both return the same rows in the same order. Where they would differ, the plan stays on the operators.

query/df.rs

The same file at every size

The segment a program maps is the segment a server or a shard serves, so the file format, the SQL, the schema and the Python methods stay the same from a laptop to a cluster. From a file to a cluster.
